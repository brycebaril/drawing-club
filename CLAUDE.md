**Auth/RBAC implementation notes** (see `src/auth.ts`, `src/proxy.ts`, `src/lib/auth/*`):
- RBAC is enforced in `src/proxy.ts` — Next.js **renamed "Middleware" to "Proxy" in v16**; same mechanism, new file/export name (`export default` in `proxy.ts`, not `middleware.ts`). Docs still say "middleware" in places since that's the conceptual role — don't recreate a `middleware.ts` file if you see the old name.
- Proxy defaults to the **Node.js runtime** in Next 16 (no opt-in, and setting a `runtime` export in a Proxy file throws). This is what lets `src/proxy.ts` query Postgres directly on every request for fresh status/role checks instead of trusting cached JWT claims.
- Auth.js Credentials provider only supports **JWT session strategy** (not database sessions) — consistent with no-ORM anyway, since DB sessions need an adapter.
- MFA is a two-step client flow: `POST /api/auth/check-credentials` validates password and reports whether a TOTP step is needed, *before* the real `signIn()` call — Auth.js's `authorize()` can't express "need more info" on its own, so don't try to collapse this into one step.
- `/api/*` is entirely excluded from `src/proxy.ts`'s matcher — API routes need their own auth handling (JSON 401s, bearer tokens), not an HTML-login-page redirect.
- **Server Functions (`"use server"` actions) must re-check auth themselves — Proxy alone doesn't cover them.** Next.js's own docs are explicit about this: a Server Function is a POST to the page it's defined on, not a separately-matched route, so a Proxy matcher change can silently stop protecting it. Every mutation in this repo (`src/app/admin/sessions/actions.ts`, `src/app/app/schedule/actions.ts`, `src/app/app/wallet/actions.ts`) derives the acting user from `await auth()` server-side and re-validates role/ownership — never trust a client-supplied user id from form data.

**Booking implementation notes** (see `src/lib/booking/*`, `src/lib/settings.ts`):
- The schedule grid's window size resolves an ambiguity between Design Doc §3.1 ("rolling 14-day window") and §5.2 (Members get a *longer* booking window than Account Holders): the grid always renders at the longest tier's width (`BOOKING_WINDOW_MEMBER_DAYS`), and each session's bookability is gated per-viewer against their own window (`src/lib/booking/sessionStatus.ts`'s `viewerBookingWindowDays`) — so an Account Holder sees further-out sessions on the grid but locked (`TooFarFuture`), which doubles as a membership upsell. Admins are unrestricted. Revisit this if it turns out not to match intent.
- `bookSession`/`cancelBooking` (`src/lib/booking/actions.ts`) row-lock the session (`FOR UPDATE`) and pick a pass with `FOR UPDATE SKIP LOCKED` inside a transaction, specifically so concurrent bookings can't oversell the last spot. Reuse this locking pattern for any future mutation touching session capacity (e.g. multi-week seat booking).
- `Waitlist_Entries` needed a uniqueness constraint on `(session_id, user_id)` that the original schema was missing — added in a follow-up migration rather than editing the original one. If you find another schema gap like this, same approach: new migration, don't rewrite history.
- **`resolveViewerEligibility`/`resolveBookingWindowEnd` (`src/lib/booking/actions.ts`) are the one shared place that resolves "can this user book at all" (email verified, account not banned/suspended) and "how far out can they book"** — extracted during a holistic code review that found `bookSeriesSeat` (`src/lib/series/actions.ts`) had silently drifted from `bookSession`'s eligibility checks by reimplementing its own window logic and skipping the email/status checks entirely. Both `bookSession` and `bookSeriesSeat` call these now; `joinWaitlist` also calls `resolveViewerEligibility` for the same reason — add any new booking-adjacent entry point here too rather than re-deriving eligibility inline.
- **`bookSession` explicitly rejects a session that's `series_id IS NOT NULL` or not `status = 'Scheduled'`** (returning `not-found` either way, so a series occurrence or a canceled session can't be booked through the generic path — series occurrences must go through `bookSeriesSeat`, which is the only place that knows about seat numbers).
- **`cancelBooking` deletes the matching `seat_reservations` row (if any) in the same transaction as releasing the pass** — a plain `cancelBooking(userId, sessionId)` call was silently leaving a stale `seat_reservations` row behind for series bookings, since it was written before series existed and never learned about the table. `cancelSeriesSeatDate` and the generic `cancelBooking` can both legally touch the same `session_id` row, so both must clean it up.
- **Pass selection is FIFO by `passes.created_at`, not `id`.** The schema had no creation-time column on `passes` at all — `ORDER BY id` (a random `gen_random_uuid()`) was standing in for "oldest first" and had been since Phase 3, silently wrong the whole time since it has no chronological meaning. Added in a follow-up migration (`passes-created-at`, same append-a-migration convention as the `Waitlist_Entries`/`seat_reservations` constraint gaps above) plus a composite index on `(owner_id, status, created_at)`; both `bookSession` and `bookSeriesSeat` now `ORDER BY created_at, id` (the `id` tiebreak only matters for two passes granted in the same instant). Matters beyond cosmetics because `effective_price` is per-pass, so which pass gets consumed first affects yield/ROI accounting.
- **`joinWaitlist` runs the same eligibility checks as booking** (verified email, account not banned/suspended) — it previously let a suspended account join a waitlist it could never actually claim a spot from, since nothing gated it the way `bookSession` was gated.

**Admin/audit implementation notes** (see `src/lib/audit/log.ts`, `src/lib/auth/requireAdmin.ts`, `src/app/admin/users/*`):
- `writeAuditLog()` is the *only* place that inserts into `system_audit_logs` — every admin/volunteer mutation calls it (including Phase 3's session creation and the wallet's test-pass grant, retrofitted in Phase 4). Don't add a new ad hoc `INSERT` for a new mutation; call it instead.
- `requireAdmin()` (`src/lib/auth/requireAdmin.ts`) is the shared Server Function guard for admin-only actions — reuse it rather than re-inlining the `auth()` + `getUserAuthContext()` + role-check pattern.
- **Redirecting a Server Action back to a page reachable via a prefetched `<Link>` can serve stale data** — Next.js's client Router Cache can hold the pre-mutation RSC payload for that path even though the redirect lands on the right URL. Fix: call `revalidatePath(path)` (from `next/cache`) right before every `redirect()` in a mutating action. Bit us concretely on `/admin/users/[id]` (reachable from the nav's admin links — see the Navigation implementation notes below) — applied proactively to every mutating action in the app (`admin/sessions`, `app/wallet`, `app/schedule` included), not just the one that broke.
- **Don't reuse an `id` attribute across two forms rendered on the same page.** Two "Reason (required)" fields with duplicate `id="reason"` (one per form) silently broke both `<label for>` association and Playwright's `getByLabel` targeting — no error at authoring time, just a field silently filled in the wrong place. Every form field `id` on `/admin/users/[id]` is now prefixed per-form (`status-reason`, `grant-reason`, etc.) — keep that convention on any page with multiple forms.
- Membership expiration needed no new mechanism — `MBR` was already fully derived (`roles.ts`), so nothing "flips" when a membership lapses. `Membership_History` is treated as strictly append-only (each admin adjustment is a new row, never an edit to an old one), matching how `System_Audit_Logs` is treated.
- **`removeVolunteerRoleAction` checks the `DELETE`'s row count before writing an audit log entry** — a holistic code review found it was unconditionally logging `VOLUNTEER_ROLE_REMOVED` even when the target user didn't actually hold that role (a no-op `DELETE`), which would have produced a misleading audit trail entry for an action that didn't happen.
- **`getUserAuthContext` (`src/lib/auth/roles.ts`) runs its user-row and volunteer-roles queries via `Promise.all`** rather than sequentially — it's called on effectively every authenticated request (Proxy, every `requireAdmin()` call), so the two independent round-trips were pure latency with no ordering dependency between them.

**Recurring session implementation notes** (see `src/lib/recurrence/*`, `src/lib/sessions/*`, `src/app/admin/sessions/*`):
- No scheduler infra exists yet (EventBridge is unprovisioned AWS work) — occurrences are generated up to a fixed 90-day horizon (`ROLLFORWARD_HORIZON_DAYS`, `src/lib/recurrence/generate.ts`) instead of on-demand per date. `generateSessionsForRule(ruleId)` always resumes from the latest already-generated occurrence (`max(start_time)` for that rule), so it's naturally idempotent — calling it again (via `pnpm rollforward`, or the admin "Generate more sessions" button) never regenerates or duplicates a date. When real scheduling lands, point it at `rollforwardAllRules()` — don't redesign the generation logic itself.
- **Cancellation (Phase 5) sets the rule's own `end_date`, not a new rule row.** `recurrence_rules` has `superseded_by_rule_id` in the schema but it's dead — never read or written. "This-and-future" cancellation cancels every `Scheduled` session on the rule from the clicked occurrence forward and sets the rule's own `end_date` to the day before it (`src/lib/recurrence/actions.ts`'s `endRuleBefore`), so rollforward naturally stops generating past that point. Rule *editing* (Phase 7, see below) deliberately follows the same "mutate the one rule row in place" philosophy rather than starting to use `superseded_by_rule_id` — see the Phase 7 notes for why.
- **"This-and-future" and "entire series" are deliberately different**, not two names for the same cancel-everything-upcoming action: this-and-future only touches occurrences at or after the *clicked* one (`start_time >= clicked.start_time`) — an earlier still-upcoming occurrence on the same rule survives untouched. Entire-series touches every `Scheduled` occurrence with `start_time > now()` regardless of which one was clicked. Both share `cancelFutureSessionsForRule(ruleId, fromDate)` (`fromDate: Date` vs. `null` is exactly this distinction) and its pure, DB-free selection core `selectSessionIdsToCancel()` — that function is what `actions.test.ts` exercises directly against a fixture, rather than hitting Postgres, to pin the semantics down.
- All admin session cancellation (one-off included) funnels through one function, `releaseAllBookingsForSession(sessionId)` (`src/lib/booking/actions.ts`) — releases every booked pass on that session (any owner), computes "was it full" once before releasing anything (so a multi-pass release doesn't make its own waitlist broadcast a no-op), and is a safe no-op if the session is missing or already `Canceled`.
- **`loginAsUser` (`e2e/helpers.ts`) navigates to `about:blank` before clearing cookies — this fixes a real, previously-undiscovered bug, not a defensive nicety.** `e2e/recurring.spec.ts` used to hang indefinitely (confirmed against a 5-minute timeout, not just slow) at its second `loginAsUser` call, deterministically, even fully isolated — bisected via `git stash` against the pre-Phase-8 commit and confirmed pre-existing, unrelated to any one phase. Root cause: `src/proxy.ts`'s guest-only guard for `/auth/login` (redirects an authenticated request straight to `/dashboard`, never rendering the login form) fired even after `clearCookies()`, because a still-in-flight request from the *previous* page — production-mode `<Link>` prefetching from the nav (now `SiteNav`), or `SessionProvider`'s mount-time session fetch, neither excluded by `proxy.ts`'s matcher — raced `clearCookies()` and kept the session looking valid at the exact moment `/auth/login`'s request was evaluated. `recurring.spec.ts` was the only spec file that reached its second login via a hard `page.goto()` with *no* further page interaction first, leaving zero elapsed time for that prior page's background requests to settle; every other multi-login spec file has real round-trips (form fills, selects) in between, which happened to give the race time to resolve on its own. The `about:blank` hop forces Chromium to discard the previous page's in-flight requests before `clearCookies()` runs, closing the race for every spec file that calls `loginAsUser` more than once — not just the one that happened to expose it.
- `src/lib/sessions/shared.ts` must stay pure constants only (`SESSION_TYPES`, `DAYS_OF_WEEK`) — it's imported by a `"use client"` form component (`RecurrenceRuleForm.tsx`). `resolveHostUsername()` lives in the separate `src/lib/sessions/host.ts` specifically because it imports `@/lib/db/pool` (`pg`); importing it from a client component drags `pg`'s Node built-ins (`tls`, `util/types`) into the browser bundle and breaks the production build with `Module not found` errors that never show up in `pnpm lint`/`pnpm typecheck` — only in `pnpm build` (which `pnpm test:e2e`'s webServer runs). Keep this split when adding anything else to that module: any server-only (DB, Node API) code goes in a separate file from constants a client component might import.
- **The `login_attempts` rate limiter is IP-scoped, not just per-account** (`src/lib/auth/rateLimit.ts`: 5 failed attempts / 15 min, `identifier = $2 OR ip_address = $3`) — `e2e/auth.spec.ts`'s banned-account test deliberately produces one real failed login every run. Re-running the full `pnpm test:e2e` suite repeatedly in a short window (e.g. while debugging something else) accumulates those on `::1` and eventually locks out *every* login from localhost, cascading into what looks like unrelated tests hanging on `getByLabel('Username')` or `waitForURL`. If most/all e2e tests suddenly start timing out at the login step with no code changes to explain it, `TRUNCATE login_attempts` on the local dev DB before assuming a real bug.
- **`playwright.config.ts`'s `retries` is `1` locally (`2` in CI), not `0`** — a handful of tests (the "Join waitlist" flow in `booking.spec.ts`/`admin-users.spec.ts`) are genuinely load-sensitive: they pass reliably in isolation (`--workers=1`) but can occasionally stall for several seconds under this machine's ~10-way local parallelism, a resource-contention reality of running that many browser+DB+server workers on one dev machine, not a code bug. A retry absorbs that without masking a real regression (which would fail consistently, not once). `webServer.timeout` is `180_000`, not `120_000`, for the same class of reason — a `rm -rf .next` before a run forces a slow cold build that can genuinely exceed 120s.

**Multi-week series implementation notes** (see `src/lib/series/*`, `src/app/admin/sessions/new-series/*`, `src/app/admin/sessions/series/*`, `src/app/app/schedule/SeriesPanel.tsx`):
- Unlike recurring sessions, a series has a real entity to hold its own metadata: the `series` table (`name`, `seat_count`, `created_by`), with `sessions.series_id` now a proper FK to it (it was deliberately left FK-less in the initial schema only because no `series` table existed yet). No template/rule row is needed beyond that — a series is fully created up front (all its `sessions` rows inserted in one transaction at creation time), so unlike `recurrence_rules` there's no ongoing generation and no "end date" to manage on cancellation.
- **Booking a numbered seat reuses the exact same pass-consumption mechanics as ordinary booking** (`passes.status`/`session_id`), with `seat_reservations` as an *additional* structure recording which seat — not a parallel accounting system. This is why `releaseAllBookingsForSession` (`src/lib/booking/actions.ts`, Phase 5) already correctly releases series passes on cancellation; it was extended to also `DELETE FROM seat_reservations WHERE session_id = $1` in the same transaction (a no-op for non-series sessions) rather than growing a separate series-specific release path.
- `seat_reservations` needed a uniqueness constraint on `(session_id, seat_number)` that the original schema was missing — the same class of gap `waitlist_entries` had, fixed the same way (new migration, don't rewrite history). `bookSeriesSeat` (`src/lib/series/actions.ts`) relies on this constraint as the actual concurrency-safety mechanism (catches Postgres `23505` the same way `joinWaitlist` already does), with an upfront `SELECT` as a faster-fail pre-check, not the sole guard.
- **Booking a seat for multiple dates is all-or-nothing, in one transaction**, sessions locked in ascending `start_time` order specifically to avoid deadlocking against a *different* concurrent booking touching an overlapping set of dates in a different order. If any checked date fails (seat just taken, outside the viewer's booking window, no pass available), the whole submission rolls back and nothing is booked — deliberately not best-effort-per-date.
- **One seat per member per series is enforced server-side in `bookSeriesSeat`**, not just implied by the UI flow — a member who already holds a different seat number anywhere in the series is rejected (`different-seat-already-held`) before any locking begins. That check now runs *inside* the transaction, immediately after `BEGIN` and before any session-row locking — it originally ran against `pool` before the transaction opened, which a holistic code review flagged as a check-then-act gap (a second concurrent request for a disjoint set of sessions in the same series could both pass the pre-check before either committed). Moving it inside narrows the race; it isn't fully closed, since no schema constraint backs the one-seat-per-series invariant the way `(session_id, seat_number)` backs seat uniqueness.
- Cancellation reuses the *exact* three-way selection logic already built for recurring rules: `selectSessionIdsToCancel()` (`src/lib/recurrence/actions.ts`) is generic over any `{id, startTime, status}[]` fed to it, so the series version (`src/lib/series/actions.ts`) just queries by `series_id` instead of `recurrence_rule_id` and skips the "end the rule" step recurring needs (nothing to end — a series never regenerates). Audit log action types are deliberately prefixed `MULTIWEEK_SERIES_*` rather than reusing the existing `SESSION_SERIES_*` names, which already mean something different (a *recurring rule's* run of occurrences) — don't conflate the two "series" concepts in new audit entries either.
- The admin slot picker (`/admin/sessions/new-series`) is shaped like the real `/app/schedule` grid (reused `slotFor`/`startOfDay`/`dayIndex`/`SLOTS` helpers, now centralized in `src/lib/sessions/shared.ts`) rather than a fixed day-of-week rule — admins tick individual open Morning/Afternoon/Evening slots across any date range, letting them skip weeks non-consecutively. Slots map to fixed canonical times (`SLOT_TIMES`: Morning 10–13, Afternoon 14–17, Evening 18–21) so a checked box has a concrete time to create a session at.
- **Formatting a `Date` as a local "YYYY-MM-DD" string (or parsing one back) must use `toDateOnly`/`parseDateOnly` (`src/lib/sessions/shared.ts`), never `toISOString().slice(0, 10)` or `new Date("YYYY-MM-DD")`.** Both of the latter operate in UTC, and silently shift the calendar day by one for any server not running in UTC — the checkbox-value round-trip in the slot picker hit this for real in dev (`America/Los_Angeles`, i.e. even a *negative* UTC offset can trigger it once `setHours` gets involved), not just as a theoretical positive-offset-timezone concern.
- **e2e/helpers.ts's shared `pool` must never be closed by a spec file's own `afterAll`.** Playwright reuses worker processes across test files, so one file's `pool.end()` can poison a *different* file that later shares that worker ("Cannot use a pool after calling end on the pool") — this broke intermittently once a 6th spec file (`series.spec.ts`) shifted scheduling enough to expose it. Fixed by removing every spec file's `afterAll(() => pool.end())`; connections close naturally when the worker process exits.
- **A same-process direct call to a server action (e.g. `await bookSeriesSeat(...)` from within an e2e test) sees its own result immediately, but a browser-driven mutation followed by a fresh query from the test's own `pool` connection can briefly lag behind that commit becoming visible** — the established `expect(async () => {...}).toPass({ timeout: 5000 })` polling pattern (already used in `booking.spec.ts`'s waitlist test) is required after every browser-driven mutation a test then asserts on via direct SQL, not just the ones that "look" racy.

**Editing implementation notes** (see `src/lib/recurrence/generate.ts`'s `regenerateSessionsForRule`, `src/lib/recurrence/actions.ts`'s `updateRecurrenceRule`, `src/app/admin/sessions/recurring/[id]/*`, `src/app/admin/sessions/series/[id]/*`, `src/app/admin/sessions/[id]/actions.ts`'s `updateSessionDetailsAction`):
- **"This occurrence only" editing and rule/series-level editing are two genuinely different features, not one with a scope flag.** The single-session instance editor (type/description/capacity/host, any session regardless of `recurrence_rule_id`/`series_id`) is a plain in-place `UPDATE` with no cancellation and no regeneration — it's what Design Doc §5.4's "Capacity & Details Override Modal" actually is. Rule/series edits are cancel-and-regenerate (see below). Don't try to unify these into one code path — they have nothing in common beyond both living on `/admin/sessions/[id]`.
- **Rule editing is cancel-and-regenerate, not update-in-place, and this is why `generateSessionsForRule`'s existing resume logic (`MAX(start_time)+1`) can't be reused for it.** Canceling a session only flips its `status`; it never deletes the row or changes `start_time`. So after canceling the occurrences an edit needs to replace, `MAX(start_time)` still points at the *last canceled one* — calling `generateSessionsForRule` again would resume *past* the very range the edit needs to refill, not fill it. `regenerateSessionsForRule(ruleId, fromDate)` exists specifically to generate from an explicit anchor instead of a resume point; the two functions now share an extracted `insertSessionsForDates` helper rather than duplicating the transaction/insert loop.
- **`updateRecurrenceRule`'s two scopes are the same mechanism as cancellation's, at different anchors** — `"entire"` maps to `fromDate = null` for cancellation (`start_time > now()`, matching `cancelEntireSeriesByRuleId`) but an *exact* `new Date()` instant for regeneration; `"this-and-future"` maps to an explicit midnight-anchored `fromDate` for both. It deliberately never calls `endRuleBefore` — that's a cancellation-only concept for permanently stopping a rule; an edit keeps the rule alive under its new parameters.
- **`computeOccurrenceDates` only reasons in whole calendar days, which breaks the "entire" scope's exact-instant anchor: without `excludeStartedDates` (`src/lib/recurrence/dates.ts`), editing a rule on a day it already ran would duplicate that day's session.** Cancellation's `start_time > now()` correctly leaves an already-happened occurrence alone, but regeneration's day-truncated range start would still treat "today" as a valid candidate (same day-of-week) and insert a second session for it. `regenerateSessionsForRule` filters the candidate dates through `excludeStartedDates(dates, rule.start_time_of_day, fromDate)`, which drops any date whose combined time-of-day instant is already at/before the anchor — a no-op for "this-and-future" (whose midnight anchor is always earlier than any same-day time-of-day) and the actual fix for "entire". Found and confirmed by a holistic code review immediately after this phase shipped, not caught by the phase's own e2e coverage (which never edited a rule on its own run day) — covered by direct `excludeStartedDates` unit tests now instead.
- **Series editing has no rule-style scope choice at all** — a series is fully created up front and never regenerated, so there's nothing to anchor a "this-and-future" edit to. `updateSeriesMetadata` mutates `series.name`/`seat_count` in place (with a guard rejecting a `seat_count` reduction below the highest currently-reserved `seat_number` — the one place capacity vs. reservations actually gets validated, since `bookSeriesSeat` itself never compares counts to capacity) and syncs `max_capacity` **only on sessions still at the old seat count** — `WHERE max_capacity = $oldSeatCount`, not an unconditional overwrite, so a session an admin already gave its own capacity via the single-session instance editor isn't silently clobbered by an unrelated series-metadata save (also a code-review finding — the original unconditional version shipped and was caught right after). Adding more dates to an existing series reuses the *same* slot-picker UI and validation (`parseSlotValues`/`checkSlotConflicts`, extracted from `createSeriesAction` into `src/lib/sessions/slots.ts` specifically so `addSeriesSlots` doesn't duplicate it) via a `?seriesId=` query param that swaps the picker into "add to series" mode.
- **The single-session instance editor (`updateSessionDetailsAction`) guards against dropping capacity below the current booked count and against editing an already-`Canceled` session** — both server-side (`AND status = 'Scheduled'` on the `UPDATE`, plus an explicit status check returning an error), not just via the UI hiding the form. `bookSession`'s own capacity check only blocks *new* bookings once count ≥ max_capacity; it never notices an admin retroactively dropping capacity below what's already booked, so this action re-derives booked count from `passes` itself rather than trusting the caller. **The session row is locked (`FOR UPDATE`) before that booked-count read**, same first-step-locks-the-session-row pattern `bookSession` already uses — the original version read the count via a plain `pool.query` before opening any transaction, a check-then-act gap a holistic code review caught: a concurrent `bookSession` call could commit a booking between the read and the capacity `UPDATE`, pushing booked-count past the newly-lowered capacity. Locking the session row first means any concurrent booking attempt (which locks that same row as its own first step) blocks until this transaction commits or rolls back.
- **`releaseAllBookingsForSession`'s booker-notification loop wraps each `sendEmail` call in its own try/catch** — one bad address (once the email stub is replaced with a real sender) shouldn't stop the remaining bookers from being notified or skip the waitlist broadcast that follows the loop.
- **Canceling any session now emails every booker it released** — `releaseAllBookingsForSession` (`src/lib/booking/actions.ts`) was extended to look up each released pass's owner and send a "your booking was canceled" email, fixing a real gap in *every* cancellation path (one-off, recurring three-way, series three-way, and the new edit-driven cancel-and-regenerate all funnel through this one function) — not something scoped to just the new edit feature. Both `/admin/sessions/[id]`'s cancel buttons and the rule-edit scope selector now carry static warning copy about this.
- **The `new Date("YYYY-MM-DD")`/`toISOString().slice(0, 10)` UTC-parsing bug (see the multi-week series notes above) was also live in `createRecurrenceRuleAction`'s and `editRecurrenceRuleAction`'s `startDate`/`endDate` handling** — undiscovered until this phase because no existing test's rule ever had its `end_date` land exactly on a day boundary the old resume-based `generateSessionsForRule` would notice. Fixed the same way, with `parseDateOnly`.
- **e2e tests that create recurring rules or series must pick a day-of-week offset / date range that can't collide with what *other* spec files create**, not just what the *same* file created on a previous run. `recurring-edit.spec.ts` originally reused `recurring.spec.ts`'s exact `(now.getDay() + 3) % 7` formula and collided with it every time both ran in the same suite invocation (the schedule grid only shows one session per day+slot cell); `series-edit.spec.ts` originally picked from the same random day-range as `series.spec.ts` for the same reason, and `series.spec.ts` itself originally shared "Evening" with both recurring files' hardcoded 18:00 rules. **Each of the four files that create dated sessions now claims its own exclusive `Slot` (`recurring.spec.ts`/`recurring-edit.spec.ts`: fixed weekday, "Evening" time-of-day; `series-edit.spec.ts`: "Morning"; `series.spec.ts`: "Afternoon")** rather than relying on day-offset arithmetic staying disjoint — a slot-per-file assignment is collision-proof regardless of what random day range any file picks, where trying to keep every file's day-offset ranges non-overlapping by hand is not (this broke twice: once between `series.spec.ts`("Evening") and the recurring files, and again between a first fix attempt that moved `series.spec.ts` to "Morning" and collided with `series-edit.spec.ts` instead). If a fifth spec file needs to create dated sessions, give it a slot none of these four already own, or hardcode a fixed day/time the way the recurring files do.

**Payments implementation notes** (see `src/lib/stripe/client.ts`, `src/lib/payments/pricing.ts`, `src/app/app/wallet/*`, `src/app/api/webhooks/stripe/route.ts`, `src/app/admin/transactions/*`):
- **The schema was already built for this before Phase 8 started** — `transactions`, `pass_batches`, `passes.transaction_id`, `membership_history.transaction_id`, and a fully-seeded `system_settings` pricing table all existed from the initial migration. Phase 8 is almost entirely application code wired onto an already-designed data model, not new schema design — if you're touching payments and reaching for a new column, check the initial migration first, it's probably already there.
- **Stripe Checkout (hosted, redirect-based), not Elements** — `createCheckoutSessionAction` (`src/app/app/wallet/actions.ts`) creates a Checkout Session with a server-resolved price and redirects the browser to `session.url`. Fulfillment (creating passes / extending membership) does **not** happen in this action — the user hasn't paid yet at the point it runs. It happens later, in the webhook handler, once Stripe confirms the charge.
- **Price is always resolved server-side, at checkout-session-creation time, via `src/lib/payments/pricing.ts`'s `resolvePrice`** — reads `system_settings` (`PRICE_SINGLE_PASS_STANDARD`/`_MEMBER`, `PRICE_PACK_5_STANDARD`/`_MEMBER`, `PRICE_PACK_10_MEMBER`, `MEMBERSHIP_ANNUAL_FEE`) using the same `membership_expires_at > now()` check `src/lib/auth/roles.ts` uses to derive `MBR`. Never trust a client-submitted price. **There is no `PRICE_PACK_10_STANDARD` setting** — the 10-pack is member-only (Design Doc §7.1); `resolvePrice` throws for a non-member requesting `Pack10`, and the wallet UI hides that button entirely for non-members rather than letting the request round-trip to an error.
- **Webhook idempotency is a real gap the docs never addressed** — Stripe redelivers events at-least-once. A new `processed_stripe_events` table (`event_id` as PK) is inserted first, inside the same DB transaction as the event's actual DB work; a conflict means "already handled," so the handler bails out as a no-op rather than double-granting passes or double-applying a refund. Any Stripe API call an event needs (fee lookups, payout-batch resolution) happens **before** this insert, not after — if it throws, the event must **not** be marked processed, or Stripe's retry would be silently swallowed by the idempotency check without the work ever having actually happened.
- **`checkout.session.completed` is the only event that creates `passes`/`membership_history` rows** — it reads `item`/`passCount`/`effectivePricePerPass` from the Checkout Session's own `metadata` (written server-side during session creation, so it's trustworthy despite superficially looking like "client" data) and the actual charged amount from Stripe's `amount_total` (authoritative, not re-derived from metadata). Membership renewal extends from the *later* of `now()` or the current `membership_expires_at` — renewing before expiry doesn't reset the clock to today.
- **Processing fee / net amount require a second Stripe API call** — `checkout.session.completed`'s payload doesn't include balance-transaction fee data directly; the webhook handler retrieves the PaymentIntent with `expand: ["latest_charge.balance_transaction"]` to get it. This extra round-trip happens before the idempotency-guarded transaction opens, same reasoning as above.
- **`payout_status`'s enum originally had no `Failed` value** — only `Pending`/`Paid_Out` — even though Architecture Doc §7 explicitly lists `payout.failed` as one of the "at minimum" events to handle. Added via a follow-up migration (`pgm.addTypeValue`), whose `down` is a no-op — Postgres has no `DROP VALUE` for enums short of recreating the whole type, which risks failing outright if any row already holds the new value.
- **Payout reconciliation resolves which `transactions` a payout covers by listing that payout's balance transactions** (`stripe.balanceTransactions.list({ payout: payoutId, expand: ["data.source"] })`, capped at 100) and matching each underlying charge's `payment_intent` back to `transactions.gateway_ref_id` — Stripe's `payout.paid`/`payout.failed` events don't enumerate the charges themselves.
- **Refunds are admin-initiated but webhook-confirmed, deliberately not written in one step.** `refundTransactionAction` (`src/app/admin/transactions/[id]/actions.ts`) only calls `stripe.refunds.create(...)` and audit-logs the *request* (`PAYMENT_REFUND_REQUESTED`, with a required reason, same pattern as `grantPassAction`'s manual-grant reason). The actual `transactions.refunded_amount`/`charge_status` write happens when the resulting `charge.refunded` webhook lands — kept as the single writer of charge state so a refund issued directly from the Stripe Dashboard (bypassing our admin UI entirely) still lands correctly, just without an attributable audit-log actor. Per Design Doc §7.1, a refund never auto-revokes unspent passes — that stays a separate, explicit action on the buyer's own `/admin/users/[id]` page (the `Revoked` pass status exists in the schema but revocation itself isn't built yet).
- **The dev-only `grantTestPassAction`/`GrantTestPassButton` stand-in was deleted, not merely dev-gated.** The original plan was to keep it behind a `NODE_ENV !== "production"` check, but `pnpm test:e2e`'s webServer runs `pnpm build && pnpm start` — a real production build — so that check would have hidden the button during the exact e2e run that needed it, while doing nothing to stop it from being reachable in an actual production deploy (same `NODE_ENV`). `booking.spec.ts` (the one spec that clicked it) now provisions its test pass via direct SQL instead, matching how every other spec file already sets up passes.
- **Early-bird membership renewal pricing is deferred, not implemented.** Design Doc §7.2 describes it only qualitatively ("configurable discount prior to expiration") with no eligibility-window formula and no corresponding `system_settings` key — a real spec gap, not just a missing constant. Phase 8 ships flat-rate `MEMBERSHIP_ANNUAL_FEE` renewals only.
- **Transferable pass sharing (Design Doc §6.2) stayed explicitly out of scope for this phase** — didn't need Stripe wiring to exist first, and shipped as its own later phase instead (see the Pass sharing implementation notes below).
- **`.github/workflows/ci.yml` must set `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` (placeholder values, same `ci-placeholder-secret` convention as `NEXTAUTH_SECRET`) — CI silently broke for a while without them.** `src/lib/stripe/client.ts` constructs its `Stripe` client at module-load time and throws if the key is unset; `pnpm build` fails outright (`Failed to collect page data for /api/webhooks/stripe`) since that module is imported eagerly by the wallet actions and the webhook route. Found only because a later session happened to run `pnpm build` with the var explicitly unset while chasing something else — if you add another eagerly-constructed client backed by a required env var, check `ci.yml`'s `env:` block at the same time you add it to `.env.example`, don't assume the two stay in sync automatically.

**Pass sharing implementation notes** (see `src/app/app/wallet/actions.ts`'s `sharePassAction`/`acceptTransferAction`/`declineTransferAction`/`cancelTransferAction`, `migrations/1786993348841_pass-direct-transfers.js`, `src/lib/notifications/getPendingNotifications.ts`, `src/components/NotificationBanner.tsx`):
- **Replaces an earlier claim-code-based gift/claim mechanism, removed entirely rather than kept alongside the new flow** — driven directly by the user's own hands-on manual testing feedback: every pass must have a real owner at all times, never sit ownerless waiting for whoever holds a code. `passes.owner_id` now never goes `NULL`. A pending transfer is tracked via `pending_recipient_id` (new column) while `status` stays `'Assigned'` — already excluded from `bookSession`/`bookSeriesSeat`'s `WHERE status = 'Available'` pass-selection, so no query changes were needed to keep a pending pass unspendable by the sender. `passes.claim_code`/`claimed_at` and the `claim_attempts` rate-limit table (and `src/lib/auth/rateLimit.ts`'s `isClaimRateLimited`/`recordClaimAttempt`) were dropped outright, not deprecated in place — `claim_note` was renamed to `share_note` (drop + re-add, matching this codebase's migration style, with a data-preserving `UPDATE` before the drop). `/app/wallet/claim` and its rbac stub are gone; the recipient is identified by username directly, no code or link involved.
- **Share initiated → accepted/declined/cancelled is a state machine entirely on the `passes` row itself**, all four transitions locking the row (`FOR UPDATE`) inside a transaction and re-checking state before mutating, same discipline the code it replaced already had: sharing sets `sender_user_id`/`pending_recipient_id`/`share_note` and flips `status` to `'Assigned'` (owner unchanged — still the sender); accepting flips `owner_id` to the recipient, clears `pending_recipient_id`, and sets `status` back to `'Available'` (a claimed pass transitioning straight to `'Available'`, never a separate "claimed" state, is unchanged from the old mechanism — `bookSession`/`bookSeriesSeat` still need zero changes to pick up a newly-accepted pass); declining and cancelling both just clear `pending_recipient_id`/`sender_user_id` and revert `status` to `'Available'`, leaving `owner_id` with the sender — a decline (recipient-initiated) and a cancel (sender-initiated) are the same end-state reached by two different actors with two different authorization checks (`acceptTransferAction`/`declineTransferAction` require the caller to be `pending_recipient_id`; `cancelTransferAction` requires the caller to be `owner_id`).
- **Deliberately doesn't use the terminal `Revoked` status for a declined/cancelled transfer.** Design Doc §6.1's `Revoked` is framed around the org reclaiming value (e.g. after a refund); a recipient declining or a sender changing their mind before anything was spent is a different scenario, and reusing `Revoked` there would destroy a pass that was already paid for over nothing more than a change of heart.
- **Batch generation (`/admin/passes/new-batch`) and peer-to-peer sharing are one mechanism, not two.** Per the user's explicit "one owner for the whole batch" decision, `createBatchAction` now requires an existing member's username up front and inserts every pass in the batch with `owner_id` set directly and `status = 'Available'` — no claim step, no codes generated at all. That owner then shares individual passes onward via the exact same `sharePassAction` any member uses; `e2e/admin-passes.spec.ts`'s batch test proves this end to end (batch creation → immediate onward share).
- **`revokePassAction`'s scope changed from "unclaimed batch inventory" (`owner_id IS NULL`) to "any unspent transferable pass"** (`is_transferable = true AND status IN ('Available', 'Assigned')`) — "unclaimed" isn't a concept that exists anymore under direct ownership, so admin revocation is now scoped by spend-state instead of provenance. Still admin-only, still reason-required and audit-logged. `reissueClaimCodeAction` and its UI were deleted outright — meaningless once codes don't exist.
- **New standing notification banner, not scoped to pass sharing specifically** — added per explicit user request during plan review ("a banner/notification component... for passes to claim or other possible CTA events"). `getPendingNotifications(userId)` (`src/lib/notifications/getPendingNotifications.ts`) returns an appendable `{message, ctaLabel, ctaHref}[]`, currently with one check (pending incoming transfers); a future addition (unverified email, an expiring membership) is just another entry pushed onto the same array. `NotificationBanner` is a self-contained async Server Component that calls `auth()` itself — rendered once, from inside `SiteNav` (see the Navigation implementation notes below), covering every authenticated page including an admin who's also a member with a pending transfer. Styled distinctly from `[role="status"]`/`[role="alert"]` in `globals.css` (`.notification-banner`) since those are transient post-action confirmations and this needs to read as a standing, unmissed-on-every-page prompt.
- **Also closed an adjacent gap found during the original gift/claim phase's planning, still true today: the membership-renewal webhook fulfillment grants `MEMBERSHIP_BONUS_PASSES` (`src/app/api/webhooks/stripe/route.ts`'s `MembershipRenewal` branch)**, a real seeded `system_settings` value — without it there'd be no real-world way for an ordinary member to ever hold a transferable pass to share, only admin manual grants could produce one.
- **`e2e/pass-sharing.spec.ts` replaces the deleted `e2e/gift-claim.spec.ts`** — share+accept, decline, cancel, share-to-nonexistent-username rejection, and the notification banner appearing on an unrelated page (`/dashboard`) before the recipient ever visits `/app/wallet` and clearing after they respond. Same disclosed Stripe-fee-lookup coverage gap as before (`checkout.session.completed`'s fee lookup is a real authenticated Stripe API call no placeholder key can satisfy) — the sharing mechanics themselves are fully covered, all reachable without Stripe.

**Ops workspaces implementation notes** (see `src/app/ops/*`, `src/lib/auth/requireOpsRole.ts`, `src/lib/ops/payouts.ts`, `scripts/generate-payouts.ts`):
- **`models`, `session_model_mapping`, `session_notes`, `model_payout_reports`, and both `checked_in` columns (`passes`, `seat_reservations`) had existed since the initial migration with zero application code touching any of them** — same "schema exists, nothing built" shape as every prior phase.
- **`requireOpsRole(allowed: Role[])` (`src/lib/auth/requireOpsRole.ts`) mirrors `requireAdmin`, but takes the allowed roles as a parameter** rather than hardcoding `ADMIN`, since unlike admin-only pages, each ops workspace is gated to a different volunteer sub-role (or set of them) and those sub-roles aren't mutually exclusive. It only proves route-level access — it does **not** know about per-session scoping.
- **Check-in is additionally resource-scoped: a `VOL_HOST` may only check in / add notes on a session they're the assigned host of** (`sessions.host_user_id = ctx.id`); `VOL_MBR`/`ADMIN` are unscoped. Per SecurityDocument §3, the RBAC matrix is route-level only and can't express per-resource ownership, so `requireCheckInAccess(sessionId)` (`src/app/ops/check-in/[sessionId]/actions.ts`) re-derives and re-checks this scoping itself on every mutation, and the page does the same check independently before rendering — same "Server Functions must re-check auth themselves" discipline as the rest of the app.
- **`array_agg` over a column typed as a custom Postgres enum (here, `volunteer_roles.role`) needs an explicit `::text` cast before aggregating, or node-pg returns the raw wire-format string (e.g. `"{SessionManager}"`) instead of a parsed JS array.** node-pg's built-in type-OID parser table only covers built-in types (and their array variants); a custom enum's array type gets its own OID with no registered parser, so the driver falls back to returning it unparsed. Calling `.map()` on that string in `describeAuthorRole` (`src/app/ops/check-in/[sessionId]/page.tsx`) threw inside the Server Component render, which Next.js surfaced only as a generic "A server error occurred" page with no server-log output reaching the terminal — the query itself ran and returned correct data even while the render crashed, which is what made this slow to isolate. Fixed by aggregating `vr.role::text` instead of `vr.role`. **A second, pre-existing instance of the exact same bug was found in `/admin/users/page.tsx` (Phase 4, predating this fix) during the user's first hands-on manual testing pass** — `row.volunteer_roles.map is not a function` on the users list page, same missing `::text` cast, same fix. It went undetected because no e2e spec had ever navigated to `/admin/users` itself (only `/admin/users/[id]`) — `e2e/admin-users.spec.ts` now has a dedicated regression test for the list page. Grepped the full codebase after fixing both; these two were the only `array_agg` call sites that existed. Watch for the same pattern in any future `array_agg`/`ARRAY_AGG` over an enum-typed column, and consider that a query working correctly in isolation (verified by direct SQL) doesn't mean the render path consuming it is safe — this bug class only ever surfaces once real data with an actual non-empty array reaches the `.map()` call.
- **Model roster management is deliberately deferred** — no `/admin/models` CRUD page this phase. `scripts/seed.ts` seeds a handful of models directly so `/ops/model-booking` has something to assign against locally; Model Booker volunteers have no self-service "add a model" UI yet.
- **Session notes still render as plain escaped text, not markdown**, even though SiteOutline's UI sketch calls the textarea "rich markdown" — true when written (no markdown-sanitization utility existed anywhere in the codebase yet), and left as-is even after the CMS phase added one (`src/components/Markdown.tsx`), since upgrading session notes wasn't asked for and is a one-line swap whenever it is. Plain text via JSX's default escaping (no `dangerouslySetInnerHTML`) is safe by default and stores into the same `content` column either way, so upgrading to real rendering later needs no data migration.
- **`sessions.model_required boolean NOT NULL DEFAULT true` is a new column** (Design Doc §9.2 describes declaring a session's model requirement at creation time, but no column backed it). `/ops/model-booking`'s "No model required" action sets this false instead of inserting a `session_model_mapping` row; the workspace's "needs attention" filter is `model_required = true AND` no mapping row exists.
- **Payout report generation follows the exact `generateSessionsForRule`/`pnpm rollforward` split**: `generatePayoutReports(weekStart)` (`src/lib/ops/payouts.ts`) is the one function that does the work, called both by `pnpm generate-payouts [weekStart]` (`scripts/generate-payouts.ts`, mirrors `scripts/rollforward.ts`) and by the "Generate this week's report" button on `/ops/financials` — same reasoning as rollforward: no EventBridge/scheduler infra exists yet, so something has to trigger report generation manually until it does. `computePayouts` (the pure rate-multiplication/rounding core) is unit-tested separately from the DB-querying wrapper, same split as `selectSessionIdsToCancel`.
- **`model_payout_reports` needed a `UNIQUE (model_id, week_start_date)` constraint the original schema was missing** — same class of gap as `waitlist_entries`/`seat_reservations`/`passes.claim_code` before it, fixed the same way (new migration). `generatePayoutReports` relies on it for `ON CONFLICT ... DO NOTHING` idempotency, matching rollforward's own "calling it again never duplicates" guarantee rather than erroring on a re-run.
- **`MODEL_FLAT_PAY_RATE` was corrected from a seeded $60.00 to the real current rate, $115.00 (effective 2023-12-11), via a data-only migration** — not an edit to the original seed migration, same "new migration, don't rewrite history" convention. The $60 value was simply wrong, not a placeholder that changed over time.
- **The weekly payout report reproduces the real legacy email this replaces** (confidentiality notice, payment-timing reminder, current rate, an e-transfer setup note, then a per-session date/model/contact table), sent to every `Controller` + `ModelBooker` role-holder via the existing `sendEmail` stub, and is also viewable on `/ops/financials` and downloadable as CSV (`/ops/financials/csv?weekStart=`, a flat query-param route rather than nested under a single `model_payout_reports` row's id, since one report bundles every model for a given week — matching the legacy email's shape, not the DB's per-model row shape).
- **The e-transfer payment security question/answer disclosed by the user during planning was deliberately NOT hardcoded into source/git history** — it's real, sensitive organizational financial-security information. Instead, the report's payment-notes text is an admin-editable, blank-by-default `system_settings` value (`MODEL_PAYOUT_PAYMENT_NOTES`, seeded via migration with an empty default) that an admin fills in post-deploy. Treat any other real credentials/secrets disclosed in planning conversations the same way — settings-store or environment config, never a literal in a migration or source file.
- **Financial reconciliation is explicitly out of scope** — the user named it a longer-term to-do, not part of this phase. `/ops/financials` only ships payout-report generation/viewing/CSV export plus a simple pass-sales/membership-renewal totals summary (aggregating `transactions` by `item_type` over a trailing window, reusing `/admin/transactions`'s query shape).
- **`generatePayoutReports` counts a model as "worked" a session only if that session's own status isn't `Canceled`** at generation time — a model mapped to a session that's later canceled doesn't get paid for it, matching the intent of a report that should reflect what actually ran.

- **The Stats API was explicitly prioritized over deferring it, for a specific reason: the user wants to use Claude Code itself as the primary consumer**, querying `/api/stats/*` directly from a terminal/agent session rather than only through the `/admin/dashboard` UI. That's why a fixed-value local-dev key is seeded via migration (see below) instead of requiring a UI round-trip first, and why this section exists — a fresh Claude Code session with no memory of this phase needs to be able to pick this up cold.
- **API keys are a separate credential surface from the member-facing Auth.js session flow** (Design Doc §10 / ArchitectureDocument.md §9) — hashed at rest with the exact same `randomBytes(24).toString("base64url")` + SHA-256 pattern as `passes.claim_code` (`src/lib/payments/claimCode.ts`), mirrored into `src/lib/auth/apiKey.ts` rather than imported, since this isn't a payments concern. `api_keys.key_prefix` (first 12 raw chars) lets the admin UI identify a key without ever being able to show the full value again after creation — same one-time-visible-secret shape as a claim link, including the same `redirect(url-with-secret-in-query-param)` fix (`src/app/admin/api-keys/actions.ts`'s `createApiKeyAction`) the gift/claim phase already had to apply, for the identical reason: the form component would otherwise unmount on the action's own route refresh before the secret could ever be read.
- **A seeded, fixed-value dev key** (`dev-stats-api-key-do-not-use-in-production`, all scopes, name `"Local dev (Claude Code)"`) is inserted by a data-only migration — same "new migration, don't rewrite history" convention as every other seed-via-migration value in this codebase, and the same "seed for local dev convenience" precedent as the ops-workspace models/volunteer-role seeding. **Not for production** — a real deployment issues real keys via `/admin/api-keys` instead.
- **Report scopes are a fixed, shared taxonomy** (`src/lib/reporting/scopes.ts`'s `REPORT_SCOPES`: `users`, `attendance`, `revenue`, `audit_logs`, `flags`) — one per dashboard section and one per `/api/stats/*` route, so a key's `scopes` array and an endpoint's required scope always speak the same vocabulary. **`REPORT_SCOPES` had to live in its own module, not inside `src/app/admin/api-keys/actions.ts`** — a `"use server"` file can only export async functions (a real Next.js build-time constraint, not a lint nicety), so a plain `const` array exported alongside the Server Actions broke the production build (`pnpm build`, which `pnpm test:e2e`'s webServer runs) with "A 'use server' file can only export async functions, found object" even though `pnpm lint`/`pnpm typecheck` both passed. Same class of gap as the client/server module-split lesson from Phase 5 — a constraint that only surfaces at build time, not at lint/typecheck time.
- **Every `/api/stats/*` route still passes its scope as a string literal (`requireApiKeyScope(request, "users")`), but that literal is now type-checked against `REPORT_SCOPES` rather than accepted as plain `string`.** A holistic code review flagged the untyped version as a silent-drift risk — a future rename in `REPORT_SCOPES` (`src/lib/reporting/scopes.ts`) wouldn't have broken the build, only produced a confusing runtime 403 for a correctly-scoped key. Fixed by exporting `ReportScope = (typeof REPORT_SCOPES)[number]` and typing `requireApiKeyScope`'s `scope` parameter (`src/lib/auth/apiKey.ts`) against it — a mismatched literal is now a `pnpm typecheck` error, confirmed by deliberately introducing one during the fix. No route file needed to change; the existing literals already matched.
- **`/admin/dashboard` and `/admin/api-keys`'s page components don't call `requireAdmin()` themselves** — confirmed by checking every existing `/admin/*` page (`/admin/audit-logs`, `/admin/transactions`, etc.): none of them do, since Proxy's `/admin/*` route rule (`allow: []`, ADMIN-only via the implicit rule) is a plain, non-resource-scoped check that fully covers page-level access on its own. Only the *mutating* Server Actions (`createApiKeyAction`, `revokeApiKeyAction`) call `requireAdmin()`, matching the codebase-wide "Server Functions must re-check auth themselves" rule — Proxy doesn't cover Server Function POSTs, only page renders.
- **`/api/stats/*` routes handle their own auth entirely** (`requireApiKeyScope` in `src/lib/auth/apiKey.ts`) — `/api/*` is excluded from `src/proxy.ts`'s matcher, same as `/api/webhooks/stripe`. A request with no/malformed `Authorization` header or an unrecognized/revoked key gets `401`; a real key missing the endpoint's required scope gets `403`. Every successful request touches `last_used_at` so a stale key is visible in the `/admin/api-keys` list.
- **`array_agg`/custom-enum and `text[]` are not the same trap.** `api_keys.scopes` is a plain `text[]` column (a built-in Postgres array type, not an `array_agg` over a custom enum) — node-pg's default type-OID parser table covers built-in array types natively, so `scopes` comes back as a real JS `string[]` with no cast needed. The `::text` cast workaround from the ops-workspace check-in bug (CLAUDE.md's ops-workspaces notes) only applies to `array_agg` over a *custom enum* column; don't reflexively add a cast here, it isn't needed.
- **Trend data is tables, not charts** — no charting library was added; `/admin/dashboard`'s attendance and revenue sections are trailing-12-week tables, matching `/ops/financials`'s existing presentation style, per an explicit user decision to avoid a new dependency for a first pass.
- **"System logs" on the dashboard (Design Doc §10) is a read-only tail of the *existing* `system_audit_logs` table** (`src/lib/reporting/auditLogs.ts`'s `getRecentAuditLogs`), not a new logging system — no APM/log-aggregation infra exists or was added. It's the same table `/admin/audit-logs` already queries in full; the dashboard just shows the most recent 20 rows with a link out to the full page.
- **"Open flags" reuses `/ops/model-booking`'s needs-a-model query shape for one flag type and adds a new "full session" flag** (`src/lib/reporting/flags.ts`) — "full" sums both booking mechanisms (`passes` for generic sessions, `seat_reservations` for series ones) against `max_capacity`; a session is only ever linked to one of the two, so summing both is safe rather than needing a branch on session type.
- **Financial & Reconciliation Reports (Design Doc §10's *other* reporting bullet) stayed explicitly out of scope** — the Treasurer-facing reconciliation tooling is a longer-term to-do already named separately in this file's "not yet built" list, distinct from the general Statistics Dashboard / Stats API built this phase. Don't conflate the two "reporting" concepts in future work.

### Stats API reference (for a future Claude Code session)

Base URL: `http://localhost:3000/api/stats/`. Auth: `Authorization: Bearer <key>` header. The seeded local-dev key (all scopes, **not valid outside a local dev DB seeded via `pnpm seed` after `pnpm migrate`**) is `dev-stats-api-key-do-not-use-in-production`.

```bash
curl -s http://localhost:3000/api/stats/users        -H "Authorization: Bearer dev-stats-api-key-do-not-use-in-production"
curl -s http://localhost:3000/api/stats/attendance    -H "Authorization: Bearer dev-stats-api-key-do-not-use-in-production"
curl -s http://localhost:3000/api/stats/revenue       -H "Authorization: Bearer dev-stats-api-key-do-not-use-in-production"
curl -s http://localhost:3000/api/stats/audit-logs    -H "Authorization: Bearer dev-stats-api-key-do-not-use-in-production"
curl -s http://localhost:3000/api/stats/flags         -H "Authorization: Bearer dev-stats-api-key-do-not-use-in-production"
```

`401` means a missing/invalid/revoked key; `403` means a valid key that isn't scoped for that report type. To issue a real (non-dev) key, log in as an Admin and use `/admin/api-keys` — the raw value is shown exactly once, immediately after creation.

**Admin settings implementation notes** (see `src/lib/settingsValidation.ts`, `src/app/admin/settings/*`):
- **Edit-only — no add/delete UI for settings keys.** A key only does anything if matching code reads it via `getSettingNumber`/`getSettingString`; creating an unrecognized key from the UI would be inert, and deleting one would break whatever reads it. Design Doc §12.2 says "view and modify," not "manage," and no schema change was needed — `system_settings`, its 15 seeded rows, and both typed readers already existed.
- **`Integer`/`Decimal` fields are plain `type="text"` inputs, not `type="number"`** — a native number input silently sanitizes an invalid string to empty before it's ever submitted (per the HTML value-sanitization algorithm), which would make server-side validation both untestable and functionally unreachable for real invalid input. `validateSettingValue()` (`src/lib/settingsValidation.ts`) is the actual enforced boundary, matching SecurityDocument's "server-side authority on all mutations" — the browser widget was never the real guard.
- **`Boolean` stores `'true'`/`'false'` as plain text** (the column is `text`, not a real boolean) — rendered as a checkbox, coerced in `updateSettingAction`. No live setting uses this `data_type` yet and no code reads one, but the enum value exists and the UI has to not break on it.
- **Every row is its own `<form>` with a key-prefixed field `id`** (`value-${settingKey}`) rather than one bulk-save form — simpler diffs, and this app already hit the exact "reused id across two forms on one page" bug once (`/admin/users/[id]`, Phase 4); 15+ rows on a single page makes that doubly worth avoiding proactively.
- **`updateSettingAction` reads the current value before writing, specifically so the audit-log entry can record both `oldValue` and `newValue`** (Design Doc §12.2's exact requirement) — skips the `UPDATE` (and the audit write) entirely when the submitted value equals the current one, so a no-op save doesn't create a misleading audit trail entry for a change that didn't happen (same reasoning as the ops-workspace `removeVolunteerRoleAction` fix).
- **No new "historical integrity" code was needed** — every price/setting read in this app (`resolvePrice`, `getSettingNumber`, etc.) already queries `system_settings` live at the moment of use; nothing caches a value into a transaction ahead of time, so a setting change already only affects future activity by construction.
- **`updateSettingAction` re-derives `dataType` from the setting's own DB row — it never trusts a client-supplied value for it.** The original version read `dataType` from a hidden form field and used it to pick the `validateSettingValue` branch; a request submitting a mismatched type (e.g. `String` for what's actually `Integer`) would skip numeric validation entirely and write a non-numeric string into a setting every `getSettingNumber()` caller assumes is parseable — the next read anywhere in the app (booking windows, cancellation cutoff, pricing) would throw. Found in a holistic code review and fixed by `SELECT`ing `value, data_type` together up front and using the DB's own `data_type` for validation; `SettingForm.tsx`'s hidden `dataType` field was removed since nothing reads it anymore (the prop is still used client-side to pick which input widget to render, which is fine — that's a UI decision, not a trust boundary).

**Admin passes implementation notes** (see `src/app/admin/passes/*`):
- **No new migration needed for the original batch/revoke phase** — `pass_batches`, `passes.batch_id`, and the `Revoked` value in `pass_status` had existed since the initial migration with zero application code touching any of them, and the `Revoked` pass status was explicitly flagged in Phase 8's notes as "the schema exists but revocation itself isn't built yet." Same "schema exists, nothing built" shape as several prior phases. (The later direct-ownership redesign did add a migration — see the Pass sharing implementation notes above.)
- **Bulk-generated batches deliberately create no `transactions` row** — an admin-entered `effective_price` per pass (same shape as `grantPassAction`'s manual grants, just non-zero) covers yield/ROI accounting without fabricating a `gateway_ref_id` (required `NOT NULL`, meant for a real Stripe charge) or adding a new `transaction_item_type` enum value for a payment that never went through Stripe. These batches correctly don't appear in `/ops/financials`/`/admin/dashboard`'s revenue tables, since no money moved through the payment rails those track.
- **Batch creation requires an existing owner username and assigns every pass in the batch to that one account directly** (`owner_id` set, `status = 'Available'`, no claim step) — per the user's explicit "one owner for the whole batch" decision made during manual testing, replacing an earlier claim-code-per-pass design. That owner then shares individual passes onward via the same `sharePassAction` mechanism any member uses (see the Pass sharing implementation notes above) — batches and peer sharing are one mechanism, not two.
- **Revocation scopes to any unspent transferable pass** (`is_transferable = true AND status IN ('Available', 'Assigned')`), not just unclaimed batch inventory — "unclaimed" stopped being a meaningful distinction once every pass has a real owner from creation. Still admin-only, still reason-required and audit-logged.
- **Found and fixed a real, pre-existing, previously-undiscovered bug while building this page's own status filter**: `/admin/transactions`'s identical `$1::text IS NULL OR t.charge_status = $1` filter query has been broken since Phase 8 and fails on *every* load, filtered or not (`operator does not exist: charge_status = text`) — Postgres infers `$1`'s type as `text` from the `$1::text IS NULL` clause, and that inferred type sticks for every later use of `$1` in the same query, so `charge_status = $1` then fails with no implicit `text`-to-enum cast. This was invisible because `/admin/transactions` has zero e2e coverage. Fixed both `/admin/transactions` and this page's own copy of the pattern by casting the *column* to text instead (`t.charge_status::text = $1` / `p.status::text = $1`) — `/admin/audit-logs`'s identical-looking filter is unaffected, since `action_type` is a plain `varchar`, not an enum. Watch for this same shape (`$1::text IS NULL OR enum_column = $1`) anywhere else a status-style filter is added against an enum column.
- **The weekly volunteer free-ticket grant (`src/lib/ops/volunteerPasses.ts`) has no admin-UI button anymore — removed 2026-09-03, per explicit user direction ("granting should be done via a scheduled job not by a person").** The real trigger is now `POST /api/jobs/grant-volunteer-passes` (shared-secret `Authorization: Bearer $JOB_TRIGGER_SECRET`, matching ArchitectureDocument.md §8's "protected internal API route" pattern), called weekly by `.github/workflows/grant-volunteer-passes.yml` — a GitHub Actions cron standing in for EventBridge Scheduler, which isn't provisioned yet; swapping the caller later needs no route-side change. `scripts/grant-volunteer-passes.ts` still exists as a manual/local-dev escape hatch only, not a second production path. `/admin/passes` replaced the old one-shot result banner with a standing "grants in the past 7 days" table (`volunteer_pass_grants` joined to `users` — every row there is a real grant, since the underlying function only inserts a row when `grantedCount > 0`) plus expanded copy spelling out eligibility exactly: `Active` status + the `GenericVolunteer` role (not any staff/ops role), `VOLUNTEER_WEEKLY_PASS_ALLOWANCE` tickets/week, skipped entirely (not topped up) once at/above `VOLUNTEER_PASS_WALLET_CAP` — both settings on `/admin/settings`. `writeAuditLog`'s `actorId` became optional (`system_audit_logs.actor_id` was already a nullable FK) specifically for this — a job-triggered grant has no human actor, and recording one as NULL beats inventing a synthetic "system" account this app has never otherwise needed.

**Email delivery implementation notes** (see `src/lib/email/sender.ts`, `src/lib/email/sender.test.ts`):
- **`sendEmail` falls back to the existing console-logged dev email whenever `AWS_REGION`/`SES_FROM_EMAIL` are unset, rather than eagerly throwing the way `src/lib/stripe/client.ts` does for its key.** Deliberately different from the Stripe precedent: `sendEmail` fires on nearly every ordinary local dev action (registration, cancellation, gifting, contact form), unlike Stripe which most local browsing never touches — an eager throw here would break normal local development for anyone without SES credentials configured. Staging/prod always have both vars set via Secrets Manager, so the fallback can't mask a real misconfiguration there. A consequence worth knowing: **no CI env var changes were needed** (unlike Stripe's `ci-placeholder-secret` requirement in `.github/workflows/ci.yml`) — CI has never set SES vars and will keep exercising the fallback path unchanged.
- **SES starts every new AWS account in a sending sandbox — it can only deliver to individually pre-verified recipient addresses until AWS approves a production-access request, an external multi-day review this repo's code has no ability to trigger or bypass.** This phase makes the application code correct and ready; it does not make real member-facing delivery possible on its own. Don't treat "the code is SES-backed now" as "email works in production" without confirming the AWS account has cleared sandbox review.
- **`sendEmail` never throws, matching the contract every call site already assumed under the console-log stub.** Only `src/lib/ops/payouts.ts`'s per-recipient payout email loop wraps `sendEmail` in its own try/catch defensively; the other 6 call sites (verification, booking cancellation, waitlist broadcast, model-assignment notification, gift-claim links, contact form) call it unguarded. Rather than audit and defensively wrap all 6, the real SES call itself is wrapped internally — a delivery failure (throttling, an unverified sandbox recipient, a network blip) is logged via `console.error` (picked up by CloudWatch automatically per ArchitectureDocument §12's observability baseline — no dedicated error tracker exists or was needed for this) but never blocks or rolls back the operation that triggered the email, matching the reasoning already established for `releaseAllBookingsForSession`'s per-booker email isolation.
- **`@aws-sdk/client-sesv2`'s mocked classes needed a real `function`, not an arrow function, in their `vi.fn().mockImplementation(...)`** — `sender.ts` calls `new SESv2Client(...)` and `new SendEmailCommand(...)`, and arrow functions are never constructible in JS regardless of what they return. `sender.test.ts` is this codebase's first use of `vi.mock`; watch for the same "not a constructor" failure anywhere else a `new`-invoked SDK client gets mocked this way.
- **No e2e coverage exists for the real-send path** — same disclosed-limitation shape as Phase 8's Stripe fee-lookup gap. CI/local dev never has AWS credentials configured, so the e2e suite only ever exercises the (unchanged) console-log fallback; the real SES call path is covered by `sender.test.ts`'s mocked unit tests only.

**Navigation implementation notes** (see `src/components/SiteNav.tsx`):
- **Replaces `PublicNav`/`AppNav`/`AdminNav`/`OpsNav` entirely** — driven by the user's manual-testing feedback that logging in silently cost a visitor the ability to reach `/about`/`/news`/`/contact` (the old `PublicNav` delegated straight to `AppNav`, which never rendered the public links), and that `AppNav`'s inline "if admin" links had drifted from `AdminNav`'s full set (only 3 of 8 admin pages were linked from `/app/*` pages). One component now renders everywhere; every page just returns `<SiteNav />` with no props.
- **The primary `<nav>` is the *same shape* regardless of role** (public links always present, plus an auth-dependent tail — guest gets Log in/Sign up, a member gets Dashboard/Wallet/Logout). `ADMIN`/ops-role links are never mixed into that visible list — deliberate, not cosmetic: an admin or volunteer is a participant first (books/attends sessions like anyone else), with admin/ops capabilities layered on top.
- **Admin/Ops links live behind a trailing "☰ Staff" hamburger, one `<li>` in the same `<ul>`** — originally shipped as a second, separately-styled full-width `<nav className="staff-nav">` bar, then changed to a hamburger per explicit user request ("being authenticated adds a hamburger menu that contains any Admin or Ops roles if RBAC matches"). Only rendered for a viewer who actually holds `ADMIN` or an ops role — confirmed via `AskUserQuestion` during that request, since "always show an empty hamburger for a plain member" was a live alternative. A `VOL_HOST`-only account (no standalone ops link — check-in is only ever reached from a specific session) sees no hamburger at all, same as a plain member.
- **Built with `<details>`/`<summary>`, not a client component + `useState`** — a native disclosure needs zero JS, keeping `SiteNav` a plain async Server Component, consistent with this app having no client-side nav interactivity anywhere else (and the earlier "plain CSS over Tailwind" call for the same reason: least additional machinery for the job). **`<summary>` needs an explicit `role="button"`** — Chromium's accessibility tree exposes the `<details>` element itself as `role="group"` with the summary's text absorbed into the group's accessible name, not as a separately-targetable button; without the explicit role, `getByRole("button", { name: "☰ Staff" })` in `e2e/smoke.spec.ts` couldn't find it at all. Trade-off accepted knowingly: unlike a JS dropdown, it won't auto-close on an outside click — only re-toggling the summary or navigating away (clicking a link inside it) closes it.

Doesn't affect `src/proxy.ts`'s own call to the same function — that runs outside the React render tree, so `cache()` there is just a passthrough, not a second win.

All pages now follow the outside-`<main>` convention.

Building it is a separate, larger feature (a real read-only calendar view) that wasn't part of this nav-unification request — left as a known, pre-existing gap, not newly introduced.

- **Two raw-internal-value display bugs got fixed as part of this pass, both worth knowing about for future additions in the same shape**: `bookSession`/`bookSeriesSeat`'s `reason` discriminant (`"no-pass"`, `"full"`, etc.) used to be shown to members completely unprocessed via the `bookingError` query param — `describeBookingErrorReason()` (`src/app/app/schedule/scheduleTypes.ts`) now translates every reason both functions can return; use it for any new reason value rather than re-interpolating `bookingError` directly. - **"Ticket" was already taken twice before this rename, both handled deliberately**: `/app/support` and the support-ticket system (`support_tickets`, "New ticket"/"Your tickets") already use "ticket" for a help-desk request — copy that could sit near it (the support page's own intro line, the pending-transfer notification banner) says "session ticket" instead of bare "ticket" to avoid reading as the wrong kind of ticket. Separately, `scripts/legacy-migration/ticketPricing.ts` already used "ticket" for the *legacy* Robostrar system's own unit of attendance (a genuinely different, unrelated historical concept) — that file's vocabulary was intentionally left alone, since it describes the legacy source data, not this app's UI.
- **The word "pass" is deliberately freed, not reused for anything new.** Per direct discussion with the user: the legacy system's "ticket" originally meant a time-bound *unlimited* access grant (buy one, attend anything in a date range) — never built there, unlikely to return, but if it ever is: **"ticket" = today's discrete single-session credit, "pass" = a possible future time-bound-unlimited product** (a day pass, week pass, season pass — the ordinary English sense of "pass"). Don't reach for "pass" as a synonym for anything else before that's actually scoped; it's the one deliberately-reserved word in this app's vocabulary.

## Core domain concepts

These rules recur throughout the spec and are easy to violate accidentally when implementing a feature in isolation:

- **Passes are the booking currency**, not direct payment. Standard passes are non-transferable and bind to a user; transferable passes must be explicitly assigned to a user before they can be spent. Every pass records an `effective_price` at creation time (even $0.00 for comp/volunteer passes) for yield/ROI accounting — never leave this null.
- **Cancellation is time-gated, not blocked.** Passes only return to a user's balance (refund) if canceled before `CANCELLATION_CUTOFF_HOURS` (default 24h) prior to session start. **Revised 2026-08-19**: canceling inside the cutoff is still allowed — it just forfeits the pass (marked `Forfeited`, a status distinct from `Revoked`: Forfeited means money was collected and deliberately not refunded, Revoked means the org reclaimed value) instead of refunding it, and the freed seat is still offered to the waitlist. The UI shows a lock icon and requires an explicit confirmation checkbox before the no-refund cancellation submits — the original "cancel action must be disabled" behavior was a real, deliberate design choice that got revised after real usage showed the all-or-nothing lock didn't match what members actually wanted (being able to free the seat for someone else even at the cost of the pass).
- **Booking windows differ by tier**: Account Holders see/book a shorter forward window than active Paid Members (`BOOKING_WINDOW_ACCOUNT_DAYS` vs `BOOKING_WINDOW_MEMBER_DAYS`). "Paid Member" is a derived status from membership history (`valid_from`/`valid_until`), not a stored role flag — check current membership validity, don't cache tier on the user record.
- **Multi-week series use numbered seats**, not general admission. A member picks one seat for the whole series (not a different seat per date) and can book a subset of dates for that seat; the remaining dates for that seat stay open to others. Pass deduction is per-date-booked, not per-seat. See the implementation notes below for how this is built.
- **Waitlist is a notification list, not a queue.** A cancellation triggers a broadcast email to everyone waitlisted; the freed spot is first-come-first-served. Don't implement auto-promotion of the "next" waitlisted user.
- **Config is data, not constants.** Pricing, cutoffs, booking windows, capacity defaults, and payout rates live in an admin-editable settings store (Section 12.1 of the design doc), each change audit-logged with old/new value. Changing a price must never retroactively alter historical transactions or already-spent pass values.
- **All state-changing admin/volunteer actions are audit-logged** (refunds, manual pass grants, bans, membership adjustments, setting changes) — this is a first-class requirement, not incidental logging.
- **Model assignment is decoupled in Phase 1**: models request sessions through a separate legacy system; the Model Booker volunteer manually mirrors assignments into this app. Don't design model-facing self-service booking yet — that's explicitly out of scope until Phase 2 (see Section 14, Open Questions).
- **Recurring sessions vs. multi-week series are different concepts** — don't conflate them. `series_id` links a session to a Section 6.5 numbered-seat multi-week series (e.g. a 4-week Extra Long Pose); `recurrence_rule_id` links it to a Section 9.2 indefinitely-repeating recurring session (e.g. "every Monday evening"). A session has at most one of the two, never both.
- **Canceling a recurring occurrence is a three-way choice**: this occurrence only, this-and-future (ends the rule as of the day before the clicked occurrence — see the recurring implementation notes above), or the entire series. Past instances are never touched by any of the three.
- **Canceling a multi-week series occurrence is the same three-way choice**, but simpler underneath: a series has no "end the rule" step (it's fully created up front, never regenerated), so this-and-future/entire-series just mark the relevant `sessions` rows `Canceled` and release their seats. User-side series cancellation is per-date only — there's no bulk "cancel my whole series booking" action.
- **Editing (Phase 7) is a separate concern from the three-way cancel scope, not a variant of it.** A single session's own details (type/description/capacity/host) can be edited in place regardless of whether it's one-off, recurring, or series-linked. A recurring rule can be edited with a this-date-forward/entire-rule choice, which cancels-and-regenerates affected occurrences rather than mutating them in place. A series' name/seat-count can be edited, and more dates can be added to an existing series — but a series has no this-and-future-style bulk edit, since it's never regenerated. See the editing implementation notes below.
- **Passes never expire**; standard/transferable passes stay in a balance until spent, refunded, or admin-revoked. Don't add expiration logic unless this changes.
- **Booking/purchasing requires a verified email** (`email_verified_at` on Users) — enforce this server-side on the mutation, not just as a registration-flow UI gate.
- **No sales tax handling** — listed prices are final; this is a documented assumption (Design Doc §7.1), not an oversight.

## Roles & access

Nine access levels gate the route tree: `GUEST`, `ACCT`, `MBR`, `VOL_HOST`, `VOL_MKT`, `VOL_MBR`, `VOL_CTRL`, `VOL_SUPPORT`, `ADMIN`. Volunteer sub-roles are additive on top of a base account, not separate account types — a user can be `MBR` + `VOL_HOST` simultaneously. Volunteer sub-roles are also **not mutually exclusive with each other** — a user can hold multiple at once (e.g. `VOL_HOST` + `VOL_MKT`), stored as multiple rows in `Volunteer_Roles` rather than a single-value field; route access is granted if *any* held role permits it. `SiteOutline.md` §4 has the full route-by-role access matrix; consult it directly rather than re-deriving visibility rules when adding a page. `ADMIN` and `VOL_CTRL` accounts require MFA to log in.

Route zones map to three areas: `/`, `/about`, `/schedule`, `/news`, `/contact`, `/auth/*` (public), `/dashboard` + `/app/*` (any authenticated member), `/ops/*` (specific volunteer roles) and `/admin/*` (admin-only). Several member interactions are modal states mirrored into query params (e.g. `/app/schedule?session_id=:uuid`) rather than separate routes — see `SiteOutline.md` §5.1 for the deep-linking convention to preserve when adding new modals.
