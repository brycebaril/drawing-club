## Financial reconciliation implementation notes

(see `src/app/ops/financials/*`):
- **This phase was almost entirely new report/UI work on top of already-existing data, not new schema** — Phase 8's Stripe webhook handler already stamps `transactions.payout_batch_id`/`payout_status`/`processing_fee`/`net_amount` on every row, and `/admin/transactions/[id]` already displayed all of it per-transaction. What was missing was seeing it *grouped by payout batch* (the actual "does this bank deposit match our records" question Design Doc §7.3 describes) and being able to export any of it.
- **Extends `/ops/financials` rather than adding a new page, on purpose** — SiteOutline frames `VOL_CTRL` ("Controller") as "Financial reviewer," the closest thing this app's RBAC has to Design Doc's "Treasurer" (no distinct Treasurer role exists). Consolidating onto the Controller's existing financial home avoids a third distinct financial surface alongside `/admin/transactions` and `/ops/financials`.
- **Every new page/link here had to stay reachable without `/admin/*` access, since `VOL_CTRL` doesn't have it.** The payout-batch drill-down (`/ops/financials/payouts/[payoutBatchId]`) renders its own transaction list inline (buyer, item type, amount, fee, net, gateway reference) rather than linking out to `/admin/transactions/[id]` — that page is ADMIN-only via the `/admin/*` catch-all rbac rule, and linking a Controller into it would just dead-end at a `/dashboard` bounce.
- **Two new CSV routes mirror `/ops/financials/csv/route.ts`'s exact shape** (own auth check, since `/api/*` bypasses `src/proxy.ts` entirely; `csvEscape` helper; `Content-Disposition: attachment`): `/ops/financials/payouts/csv?payoutBatchId=` for matching one bank deposit, and `/ops/financials/transactions/csv?start=&end=` for an arbitrary date range (the "transaction histories... to assist with tax filings" deliverable). The date-range route validates `start`/`end` against a strict `YYYY-MM-DD` regex before embedding them in the `Content-Disposition` filename — the other CSV routes' query params were never attacker-reachable string content embedded in a response header before this one.
- **The existing "Sales & renewals" summary changed from a hardcoded trailing-90-days window to an admin-selectable date range** (defaulting to the same 90 days for continuity) plus a new "Total fees" column (`sum(processing_fee)`) — satisfies "processing fee breakdowns" and lets the Controller pull a specific fiscal/calendar period rather than only ever seeing a rolling window, which a tax filing generally needs.
- **Computing the default 90-day-ago date via `new Date(Date.now() - ...)` failed `pnpm lint`'s `react-hooks/purity` rule** — `Date.now()` specifically (not `new Date()` itself) is flagged as an impure call inside a Server Component's render. Fixed by capturing `const now = new Date()` once and using `now.getTime()` for the arithmetic instead — a `Date` instance method call doesn't trip the same rule, only the bare `Date.now` global does. Watch for the same class of lint failure anywhere else a relative date gets computed inline during a component's render.
- **No auto-generated tax documents (1099s, etc.)** — Design Doc says "assist... with tax filings," not automate them; the CSV exports are the deliverable, matching how this app has consistently avoided building anything beyond what's explicitly asked for (e.g. no reconciliation-report-generation-as-a-scheduled-job either, this is all on-demand viewing/export).

## Table overflow implementation notes

(see `.table-scroll` in `src/app/globals.css`, e.g. `src/app/admin/audit-logs/page.tsx`):
- **Every `<table>` across the app is wrapped in a `<div className="table-scroll">`** — a wide table (many columns, long IDs/metadata) needs to scroll within its own bounds instead of breaking out of `main`'s 960px card. Excludes the 3 grid-style `<table border={1} cellPadding={4}>` usages (`app/schedule/page.tsx`, the series slot-picker forms) — those are a fixed calendar/slot grid, a different UI pattern with no overflow complaint against it.
- **Two earlier passes at this same bug undersold the actual problem, worth remembering so they aren't repeated.** (1) `overflow-x: auto` on the table itself (`display: block`, no wrapper div) correctly contained the overflow, but left the native scrollbar as the *only* cue it existed — on a long table (200 rows on `/admin/audit-logs`) that scrollbar sits below every row, often well below the viewport, easy to never discover at all. (2) Adding a `background-attachment: local/scroll` "shadow" gradient cue on the wrapper (the well-known pure-CSS scroll-shadow technique) is real and was correctly wired, but reads as a thin, easy-to-miss sliver on a container that tall — the technique was designed for short horizontal strips, not a scrolling data table, and doesn't actually solve "the scrollbar is out of view."
- **The actual fix for a *long* table is `.table-scroll { max-height: 60vh; overflow: auto; }` plus `.table-scroll th { position: sticky; top: 0; }`** — capping the panel's own height and letting it scroll vertically too keeps the horizontal scrollbar inside the visible panel at all times, instead of hundreds of rows below it, with the header staying pinned as you scroll. On a short table (most pages here — a handful of rows) this never engages at all, since natural content height stays under the cap; it only changes behavior for genuinely long lists. The scroll-shadow gradient from the second pass was kept alongside this (harmless, marginally helpful once the container is short) rather than removed.
- **`td:has(code)` gets a `min-width: 16rem`** — `overflow-wrap: anywhere` on `td code` (needed so a JSON metadata blob, which has no spaces to wrap on, doesn't force its column out to the string's full length) has a side effect: browser table auto-layout can then shrink that column arbitrarily far, down to a single character wide with one blob spanning 10+ short lines — seen for real on `/admin/audit-logs` before this fix. The `min-width` floor keeps the column at a usable width regardless; the table only needs to scroll once a row's *other* columns also push the total past what's available.

## Media library implementation notes

(see `migrations/*uploaded-files*`, `src/lib/uploads/dimensions.ts`, `src/lib/uploads/format.ts`, `src/app/ops/cms/media/*`, `src/components/cms/MediaPickerModal.tsx`, `src/components/cms/useMarkdownFileUpload.ts`):
- **Confirmed with the user before building: record & validate dimensions, no resizing/compression** — `sharp` (or any pixel-decoding image library) stayed explicitly out of scope. `image-size` (a new, small, native-build-free dependency) reads width/height straight from an image buffer's header without decoding pixels, which is all "record & validate" needs. `readImageDimensions`/`exceedsMaxDimension` (`src/lib/uploads/dimensions.ts`) are both pure and unit-tested; the actual reject-before-storing check lives in `uploadFileAction`, run *before* `uploadFile()` so a rejected image is never actually written to S3/disk.
- **`MAX_IMAGE_DIMENSION_PX` (6000) is a hardcoded constant in `src/lib/uploads/constants.ts`, not a `system_settings` row** — same reasoning as `MAX_UPLOAD_SIZE_BYTES` right next to it: a technical/security limit, not a business value.
- **"Placement control" was also confirmed with the user, and turned out simpler than the alternatives considered (a custom Markdown attribute syntax, size presets at insert time): a single global CSS rule** (`img { max-width: 100%; height: auto; }` in `globals.css`) constrains every rendered image — Markdown-embedded and the two literal `<img>` usages (`news/page.tsx`, `news/[slug]/page.tsx`'s featured image, which had **no size constraint at all** before this, a real pre-existing gap this closed as a side effect) — to scale down and fit its container. No remark-plugin changes, no per-image markup.
- **`uploaded_files` is the first real persisted upload record** — `key`/`url`/`content_type`/`size_bytes`/`original_filename`/`width`/`height` (the last two nullable — null for a PDF, or for an image `image-size` couldn't parse despite passing the content-type allowlist) plus `uploaded_by` (`references users, onDelete: RESTRICT`, same required-attribution pattern as `pass_batches.created_by`). `CMS_FILE_UPLOADED` audit-log entries are unchanged, not replaced — the new row's id is folded into that entry's metadata for cross-reference.
- **Deleting a library entry removes only the database row, never the underlying S3/disk object** — this app doesn't scan CMS content for references to a URL, so actually deleting the stored file could silently break an already-saved page that still embeds it. An orphaned file in storage is the deliberately-accepted safer failure mode; the comment in `deleteUploadedFileAction` (`src/app/ops/cms/media/actions.ts`) says so explicitly, since it's exactly the kind of limitation a future session might otherwise "fix" into a worse bug.
- **`MediaPickerModal.tsx` follows `EditSessionModal.tsx`'s established modal conventions** (backdrop/panel/Escape-to-close/lazy-fetch-on-open) rather than inventing a new shell, and reuses the exact same cursor-insertion logic a fresh upload uses — `useMarkdownFileUpload`'s upload-completion path and the picker's selection callback both now go through one extracted `insertSnippet(file, url)` function, so there's only one place that knows how to place Markdown at the textarea cursor.
- **`uploadFileAction` calls `revalidatePath("/ops/cms/media")` unconditionally on every successful upload**, including the two callers that have nothing to do with the media library page (`NewsPostForm`'s featured-image uploader, the picker's own fetch) — harmless for them, and without it a fresh upload from the media library page's own embedded `<UploadForm />` didn't show up in the table below it until a manual reload, caught by live-testing this feature rather than by any automated check.
- **`NewsPostForm.tsx` renders two `MediaPickerModal` instances on one page** (content body, featured image) — both say "Browse existing"; nothing about the component needs a unique id (no ids at all inside it), so this doesn't hit the "duplicate id across two forms" trap documented above, but an e2e test targeting one by role/name needs `.first()`/`.last()` or a nearby-label scope.

## Org identity implementation notes

(see `src/lib/org.ts`):
- **Confirmed by the user directly, not guessed from the live site alone**: legal name "The Vancouver Life Drawing Society", DBA "Basic Inquiry" (the live lifedrawing.org site's actual brand — its page title, header, and copyright line all say "Basic Inquiry"; the legal name appears there only as a subtitle). This app's seed data previously only knew "Life Drawing Society," with no DBA at all.
- **Env vars (`ORG_LEGAL_NAME`/`ORG_DBA_NAME`), not `system_settings` rows** — a deliberate departure from this app's usual "config is data" reflex. `system_settings` is for *business* config an admin tweaks at runtime (pricing, cutoffs, booking windows); org branding is *deployment* identity, set once per instance, same category as `SES_FROM_EMAIL`/`STRIPE_SECRET_KEY`/`NEXTAUTH_URL` — already plain env vars, not settings rows. Both vars are pre-filled with the real values in `.env.example` (not left blank) — matching `NEXTAUTH_URL`'s existing precedent for a non-secret default.
- **`ORG_DBA_NAME` falls back to `ORG_LEGAL_NAME` if unset, which itself falls back to a generic default** — a fork that only bothers to set one still gets something sensible, matching `sendEmail`'s general defensive-fallback style. `src/app/page.tsx`'s legal-name tagline line only renders when the two differ, so a fork with just one name configured doesn't see it duplicated.
- **This is the first piece of the org-identity work, not the whole thing** — the five previously-hardcoded "Life Drawing Society" call sites (page metadata, the homepage `<h1>`, the verification-email subject, the MFA/TOTP issuer, plus the two test assertions that had the same literal-string problem) now read from `src/lib/org.ts`, and the seeded `static_pages` rows (about/contact/home) have real copy sourced from the live site instead of "Content coming soon" placeholders. Still explicitly deferred: linking the Constitution/Bylaws/Safety Plan/Handbook PDFs (nothing's been uploaded through `/ops/cms/uploads` yet — a dead link is worse than no link) and updating `docs/*.md` (the org's own spec documents still say "Life Drawing Society" throughout — a separate, bigger content decision than getting the live app's public pages right).
- **`CONTACT_FORM_RECIPIENT_EMAIL` (blank since it was seeded, per the CMS phase's own "real org contact info doesn't belong hardcoded" reasoning) is now set to the real address** — the one change in this pass with an actual operational consequence rather than just page copy, flagged to the user before writing it.

## Post-reporting-overhaul code review + test flakiness fixes

(commits after the reporting overhaul phase — see `src/lib/reporting/queryFilters.ts`, `migrations/*add-legacy-id-to-passes*`, `migrations/*make-users-email-case-insensitive-unique*`, `vitest.config.mts`):
- **`passes.legacy_id` is a new nullable column, same convention as `users.legacy_id`/`models.legacy_id`.** A holistic code review found `passesReport.ts`'s origin classification (`legacy`/`stripe`/`batch`/`admin_grant`) was silently misclassifying every legacy-migrated pass as `admin_grant`, since the migration scripts never linked passes back to their source row and CLAUDE.md had already documented a deliberate decision *not* to backfill `transaction_id` on migrated passes. Adding a dedicated `legacy_id` column (set by `scripts/legacy-migration/passes.ts`/`attendanceHistory.ts` at migration time) resolves this without reversing that earlier decision — `ORIGIN_EXPRESSION` in `passesReport.ts` checks `p.legacy_id IS NOT NULL` first, ahead of the now-effectively-dead-for-passes `gateway_ref_id LIKE 'legacy-%'` fallback (kept defensively, not removed). **Backfilling this on already-migrated data requires a full `--reset` re-migration run** — a plain `pnpm migrate` only adds the column, it doesn't retroactively populate it on existing rows.
- **Email login/lookup is now case-insensitive, username stays case-sensitive.** `users_email_unique` (plain column constraint) was replaced with a functional unique index on `lower(email)` (`users_email_lower_unique`) — every email-lookup query (`src/auth.ts`, `check-credentials/route.ts`, `passwordReset.ts`) now matches via `lower(email) = lower($1)`. Verified zero real case-variant collisions in the migrated dev DB before applying.
- **`releaseBookedPass` (`src/lib/booking/actions.ts`) is now exported and shared with `cancelSeriesSeatDate` (`src/lib/series/actions.ts`)** — a code review found the series cancellation path had reimplemented the exact same booked-count/refund-vs-forfeit logic inline instead of reusing it, the same "series path silently drifts from the generic path" pattern this codebase has hit and fixed several times before (see the booking/editing implementation notes in `CLAUDE.md`). `cancelSeriesSeatDate` still does its own `seat_reservations` cleanup afterward — `releaseBookedPass` only ever touched `passes`.
- **Vitest's default `pnpm test` was genuinely flaky on this dev machine, not imagined** — spawning one fork-process worker per test file in parallel occasionally missed vitest-pool-runner's startup handshake and timed out (`[vitest-pool]: Failed to start forks worker`), failing the whole run even though every individual test passed. Reproduced directly: a parallel run took ~60s (including the timeout wait) vs. ~9s running sequentially — the suite's actual test execution is under 2s, so fork-spawn overhead dominated and parallelism had negative net value here anyway. Fixed by setting `fileParallelism: false` in `vitest.config.mts` as the permanent default, rather than requiring the `--no-file-parallelism` flag by convention on every invocation.
- **Other fixes from the same review, one-line/self-contained enough not to need their own section**: `queryFilters.ts`'s `parseDateParam`/`dateRangeClause` had the same UTC-date-parsing bug documented elsewhere in this file, now fixed via `parseDateOnly` + an exclusive next-day upper bound; the admin user detail page's "Legacy activity" panel only showed audit-log rows where the viewed user was the *actor*, missing rows where they were the *target* (e.g. an admin banning someone) — now `OR`s both; `attendance.ts`'s weekly trend was counting `Forfeited` (late-canceled, never attended) passes as bookings — added `AND p.status = 'Used'`, matching `flags.ts`/check-in's existing precedent; the Passes report's CSV export and `/api/stats/passes` route were both missing filters the on-page report already had (`costBasisMin`/`Max` on the CSV route, `costBasisSource` on the API route) — an admin/API consumer filtering by either would silently get a wider, unfiltered result than the page showed; `ScheduleGrid.tsx` was constructing two `Intl.DateTimeFormat` instances per day inside its render loop instead of once, hoisted to module scope; `SeriesPanel.tsx` was independently re-fetching `CANCELLATION_CUTOFF_HOURS` via its own `getSettingNumber` call even though `page.tsx` already fetches it — now passed down as a prop instead.
- **Backfilling `passes.legacy_id` (a full `--reset` legacy-migration re-run against this same dev DB) had a real, unexpected side effect on e2e reliability: it populated a genuinely busy near-term calendar** (~2,406 real migrated sessions, many recurring, landing 1-9 per day across the next month) where the dev DB previously only held sparse test fixtures. `pnpm test:e2e` at Playwright's own default local worker count (10, on this 20-logical-core machine) went from "a handful of load-sensitive tests occasionally stall" (the pre-existing documented behavior below) to near-total mass timeouts — 10 concurrent full browser+DB+server flows against a much heavier dataset pushed ordinary page loads to multiple seconds each, blowing past the 30s per-test timeout almost everywhere. Fixed by capping `playwright.config.ts`'s `workers` to `4` locally (CI keeps its own default — it always runs against a dedicated, freshly-migrated-schema-only DB, never this legacy dataset). Confirmed the cap alone was sufficient: a re-run at 4 workers finished in under a minute with only the one already-documented flaky test.
- **Separately, that same denser calendar turned `series.spec.ts`/`series-edit.spec.ts`'s plain-random date-offset picking from "avoids stale leftover-session collisions" into "collides on a majority of candidate days"** — confirmed directly against the DB (roughly 60-70% of near-term dates already had an occupied Afternoon slot). The admin slot-picker shows an occupied date as a disabled "Booked" label with no checkbox, so a colliding pick isn't a slow test, it's a `locator.check()` that waits for a checkbox that will never exist — both files hit this as a hard, non-retriable-in-place failure (identical timeout on both the initial attempt and the retry, unlike a genuinely load-sensitive test). Fixed with a real fix, not a wider retry budget: `findOpenSlotBase()` (`e2e/helpers.ts`, shared by both files since the logic is identical modulo slot/offsets/range) queries `sessions` for the candidate date range up front and picks the smallest base offset whose whole date triple is actually free, falling back to the original unconditional offset only if every candidate in range collides. This is now a standing risk any time the dev DB carries the full legacy dataset (not a one-off from this specific migration run) — any *new* e2e spec file that picks calendar dates via plain randomization should use this helper rather than reintroducing the same class of bug.
- **`findOpenSlotBase()`'s fallback isn't fully collision-proof under repeated local re-runs**: each successful `series.spec.ts`/`series-edit.spec.ts` run permanently adds 3 more Afternoon/Morning-slot sessions inside the very window it searches next time (no DB reset between local e2e runs), so running the full suite several times in one sitting can eventually exhaust the search range and fall back to a base that does collide — seen directly in this repo's own dev loop after a third same-day re-run. Not a defect in the fix itself (a single run, or CI's per-run fresh DB, isn't affected); if this resurfaces after several same-day local e2e runs, widen `findOpenSlotBase`'s `maxBase` before assuming the underlying fix regressed.

## Quality-pass iteration 1

`findOpenSlotBase` was actually broken (not just occasionally exhausted), plus a real same-URL race (see `e2e/helpers.ts`, `e2e/recurring.spec.ts`, `e2e/series.spec.ts`, `e2e/booking.spec.ts`, `e2e/admin-users.spec.ts`) — found during a holistic "get it staging-ready" pass, not from a bug report:
- **`findOpenSlotBase`'s occupancy check (`EXTRACT(HOUR FROM start_time)`/`start_time::date` in SQL) was silently checking the wrong timezone the entire time it existed.** `start_time` is stored as whatever UTC instant the app's local server time (`America/Los_Angeles` in dev) converts to — an 18:00 Evening session lands at 01:00 UTC the *next* calendar day. `EXTRACT`/`::date` evaluate in the DB session's timezone (UTC, confirmed via `SHOW timezone`), not the app's local time, so the Evening-slot check (`SLOT_HOUR_RANGE.Evening = [18,23]`) was comparing against UTC hour 18-23 while real Evening sessions sit at UTC hour 0-6 — never matching, ever. Morning/Afternoon were checking equally wrong ranges, just less visibly since their local-to-UTC shift doesn't cross a day boundary as dramatically. This is exactly the "UTC vs. local calendar day" bug class this file documents fixing elsewhere (`parseDateOnly`/`toDateOnly`) — just never applied to this specific helper. `recurring.spec.ts`'s schedule-grid link check (`a[href*="session_id=..."]` not found) is what actually surfaced it: several same-day reruns had quietly filled every day-of-week with a same-instant collision this check should have caught from the very first run. **Fixed by computing occupancy in JS via `slotFor`/`toDateOnly` (`@/lib/sessions/shared`, the same local-time helpers the real app itself uses in `checkSlotConflicts` and `/admin/sessions/new-series/page.tsx`)** instead of SQL-side `EXTRACT`/`::date` — matching the app's own occupancy definition exactly rather than reinventing a second, divergent one.
- **A second, independent bug in the same function**: the scan window (`windowStart`/`windowEnd`) was anchored at the raw `now.getTime()` instant, not `startOfDay(now)`. Run the helper any time after a slot's local start-of-day time (e.g. after 2pm for "Afternoon"), and the unaligned window start lands *later* in the candidate day than a real same-day session's own start time, excluding it from the scan even though the app's own occupancy checks always reason in whole local calendar days. Fixed by anchoring both bounds to `startOfDay(now)`.
- **`series.spec.ts`'s `maxBase` (10) turned out too narrow once both bugs above were fixed and the check started working for real**: the dev DB's near-term Afternoon slot is solidly occupied for about the first 10 days out (confirmed directly against the DB), so every candidate base in 3..10 collided on at least one of its three far-apart offsets, every time — not occasional exhaustion, a hard wall. Widened to 13 (day1 still comfortably inside the 14-day Account Holder booking window the test's later assertions depend on).
- **Separately, a real test-authoring bug found live in `booking.spec.ts`/`admin-users.spec.ts`: `page.waitForURL(sameUrlItStartedOn)` resolves *instantly* for a Book/Join-waitlist click whose redirect lands back on the exact URL already loaded (`session_id` doesn't change)** — the same "sameUrlItStartedOn" trap this file already documents for `updateStaticPageAction`/`updateNewsPostAction` (CMS implementation notes), just newly discovered on this different action shape. Because the wait resolves without proving the mutation actually committed, the test's very next line — `loginAsUser`, whose first action is `page.goto("about:blank")` specifically to fix a *different*, previously-documented race (see the recurring-session implementation notes in `CLAUDE.md`) — discards the still-in-flight Book/Join-waitlist request before the server ever finishes processing it. Manifested as an intermittent, no-code-cause-looking failure: a waitlist row silently never created, or a session silently not yet "Full" for the next user. Fixed everywhere it was confirmed to actually bite (`booking.spec.ts`'s two Book steps and its Join-waitlist step, `admin-users.spec.ts`'s Book and Join-waitlist steps) by polling for the real DB effect (`toPass`) before the next `loginAsUser` call, not by trusting the redirect alone. **Any e2e step shaped like "click a form button whose action redirects back to the same URL, then immediately call `loginAsUser`" carries this same latent risk** — not audited exhaustively across every spec file, so treat a new instance of this shape with suspicion rather than assuming `waitForURL` proves the mutation landed.
- **Confirmed separately, not a code bug**: `next start` (a real production build, not `next dev`) serves `public/` off a boot-time snapshot — a file the local-disk upload fallback writes at runtime is unreachable (permanent 404, no self-healing short of a restart) for that server process's whole lifetime. See the Uploads implementation notes in `CLAUDE.md` for the actual fix (`src/app/uploads/[key]/route.ts`); noted here too since it was found via the exact same "run the real e2e/production-build path, don't just trust that it worked before" methodology as the two bugs above.

## Evening-slot collision fix

A real TOCTOU race, a real weekly-cadence math bug, and a large pile of stale multi-day dev-DB debris (see `e2e/helpers.ts`'s `withSlotLock`/`findOpenWeekday`, `e2e/recurring.spec.ts`) — found and fixed in direct response to an explicit user request ("fix that Evening slot collision risk now... always look to reduce test flakiness"), not a bug report:
- **`findOpenSlotBase`'s search-then-create sequence had no cross-process synchronization** — two concurrent Playwright workers could both read "day X is free" before either had committed its own creation. Fixed with `withSlotLock` (`e2e/helpers.ts`), a Postgres advisory lock (`pg_advisory_lock`/`unlock` on a dedicated connection, one numeric key per slot name) wrapping the *entire* find-then-create sequence, not just the search — a wider search range only lowers the odds of the race, a lock closes it. Applied at all slot-search call sites across `booking.spec.ts`, `admin-sessions.spec.ts`, `recurring.spec.ts`, `series.spec.ts`, `series-edit.spec.ts`.
- **A second, independent, more subtle bug found while widening `recurring.spec.ts`'s search range to work around dense legacy occupancy: `findOpenSlotBase` is the wrong tool for a *weekly recurring rule*, and using it silently passed a stale "free" result.** `findOpenSlotBase` is built for absolute date lists (one-off/series bookings, where the app creates a session on literally whatever date was checked) — but a recurring rule's actual occurrence dates are `today + (dayOfWeek - today.getDay() + 7) % 7`, then `+7` repeating; they depend only on day-of-week, never on an arbitrary day-count offset from today. The old code called `findOpenSlotBase(now, "Evening", [0,7,14,21], 3, 15)` and used the returned `base` directly as both the day-offset checked *and* the day-offset used to derive `dayOfWeek` — for any `base > 6` this checked occupancy at dates (`today+base`, `today+base+7`, ...) that the created rule would *never actually land on* (real dates land at `today+(base%7)`, `...+7`, ...), so a `base` like 15 could report "free" for dates nobody was checking while the rule silently landed on an already-occupied day. Fixed with a dedicated `findOpenWeekday(now, slot, weekOffsets)` that only ever searches the 7 real day-of-week candidates, each checked against the exact dates a rule choosing that day would actually generate.
- **Once the math was right, a structural fact came out directly against the dev DB: only 2 of 7 weekdays are genuinely open in the Evening slot** — 5 of 7 (Mon-Fri) carry a real, permanent legacy-migrated weekly recurring class from `nicholasjackiw`'s account (10:00-13:00/14:00-17:00/18:00-21:00-ish across various weekdays; only Sat/Sun have no Evening occupant). Afternoon, by contrast, only has Sunday permanently occupied (6 of 7 free) — `recurring.spec.ts` was moved from "Evening" to "Afternoon" (time-of-day isn't part of what the test exercises) specifically for the extra headroom, since Evening's 2-of-7 pool was too tight to reliably win a race against `booking.spec.ts`'s own several Evening-locked one-off tests, which — pushed onto the same 2 open weekdays by the identical legacy occupancy — were independently consuming that same scarce space under the same shared lock.
- **`recurring.spec.ts` now self-cleans its own previous run's leftover `recurring-test-%` rule before searching** — with only a handful of truly open weekdays for any single-file weekly-cadence test to search across, a leftover rule from an earlier same-day local rerun (capped at 30 days, but still `Scheduled` and still occupying whichever day it picked) can exhaust the remaining pool after as few as 2 reruns without a human remembering to clean up first. Safe because this file only ever runs as a single test instance, never `--repeat-each`.
- **The deepest cause of persistent, unexplained exhaustion turned out to be pre-existing dev-DB debris going back to 2026-08-19 — not a flaw in the fix above.** `series` held ~30 `review-fix-series-*`/`review-fix-series2-*` rows from unrelated earlier code-review sessions across several different days, plus a `"Fun Times"` series (real `brycebaril` account, sessions titled `asdfsadfs`) from earlier manual browser testing — together occupying most Afternoon weekdays and defeating even a same-day-clean verification run. None of it matched the `%-test-%`/`recurring-test-%` cleanup patterns any spec file already used, since it predated those conventions. Confirmed with the user before deleting (a meaningfully broader DB change than what was asked, and one row set was under the user's real account) — removed via one-off cleanup, not a new code path, since this class of drift isn't expected to recur now that every spec file's own leftover-cleanup conventions are in place.

## Password reset implementation notes

(see `migrations/*add-password-reset-tokens*`, `src/lib/auth/passwordReset.ts`, `src/app/auth/forgot-password/*`, `src/app/auth/reset-password/*`):
- **A new `password_reset_tokens` table, hashed-at-rest (SHA-256) the same as `passes.claim_code` was before pass sharing removed it** — `requestPasswordReset`/`consumeResetToken` never store the raw token, only its hash, matching this codebase's established secret-handling convention.
- **1-hour TTL, deliberately shorter than email verification's 24-hour window** (`src/lib/email/verification.ts`) — a password-reset link is a higher-value secret than an email-confirm link, the same reasoning most account-recovery flows use a tighter TTL.
- **Capped at 3 outstanding (unconsumed, unexpired) tokens per account within a 15-minute window** — cheap inbox-spam protection via a query against the token table itself rather than a dedicated rate-limit table, matching the precedent set by deliberately *not* re-adding a `claim_attempts`-style counter table when pass-sharing's claim codes were removed (see the Pass sharing implementation notes in `CLAUDE.md`).
- **`requestPasswordReset` never reveals whether a matching account was found** — `requestPasswordResetAction` always returns the same generic "submitted" response regardless, so the flow can't be used to enumerate registered usernames/emails. Account lookup matches **username OR case-insensitive email**, mirroring `src/auth.ts`'s own login lookup exactly.
- **Consuming a token invalidates every other outstanding token for the same account in the same transaction** — an older, still-unexpired reset link can't also be used after a newer one succeeds. Same row-lock-then-validate discipline as `consumeVerificationToken`.

## Uploads implementation notes

(see `src/lib/uploads/storage.ts`, `src/app/ops/cms/uploads/*`, `next.config.ts`):
- **First piece of a broader content push** (worked out in conversation, not yet fully built): real org identity/copy, an extensible static-pages mechanism, and a live-data Pricing page are separate, later pieces. This one exists because none of the rest can use real images or PDF documents (Constitution, Bylaws, Safety Plan, Session Manager's Handbook) without it. `.env.example` already had an `S3_BUCKET_NAME` line under a "CMS image uploads" comment before any of this was built — same "config/schema exists, nothing built" shape as several earlier phases.
- **`uploadFile()` mirrors `sendEmail`'s shape exactly**: real S3 (`@aws-sdk/client-s3`) whenever `AWS_REGION`/`S3_BUCKET_NAME` are set (reusing the `AWS_REGION` var SES already added, no new region config), a local-disk fallback under `public/uploads/` (gitignored) otherwise. Unlike `sendEmail`'s fallback, this one isn't just a dev convenience — it's what makes the whole upload path genuinely e2e-testable, unlike the Stripe fee-lookup and SES real-send gaps this codebase has otherwise accepted as disclosed-but-untested. CI never sets AWS vars (same as it never sets SES vars), so it exercises the fallback automatically; production always has both vars set, so the fallback can't mask a real misconfiguration there.
- **The storage key is always server-generated** (`randomBytes(16).toString("hex")` + an extension looked up from the *validated* content type, via `EXTENSION_FOR_CONTENT_TYPE`) — the client's filename is never trusted as the actual storage path, and (fixed by a holistic code review right after this shipped) the extension isn't trusted from the client's filename either. Deriving it from the original filename instead would have let a file named `payload.html` with a forged `image/png` Content-Type pass the allowlist check, then get stored with a `.html` key — the local-disk path infers Content-Type from the stored key's extension (see the route handler note directly below), not any validated metadata, so it would have been served back as real HTML. S3 was never exposed to this specifically (it honors the declared Content-Type header regardless of key extension), but the local-disk path — the one this feature was built to be e2e-testable through — was.
- **A file the local-disk fallback writes to `public/uploads` after the production server has already booted is NOT reliably served by Next's built-in static file handling — confirmed directly against a real `next build && next start`, not a theoretical concern.** `next start` serves `public/` off a snapshot effectively fixed at boot; a file written at runtime (i.e. every real upload, since the server is already running by the time anyone uploads anything) 404s **permanently** for that server process's lifetime — no self-healing, confirmed by polling the same URL repeatedly over several seconds and only succeeding after an actual server restart. This is exactly the class of bug `ops-cms-uploads.spec.ts`'s content-type assertion (see the 307-redirect fix above) was written to catch, but it had never actually been exercised against a genuine production build in CI/local dev until a holistic quality-pass session did so directly — every prior "passing" run of that spec had, by chance, either reused an already-warm dev server or hit an already-existing file. **Fixed with `src/app/uploads/[key]/route.ts`**, a dynamic Route Handler that re-reads the file from disk on every request (content-type resolved from the key's extension via `CONTENT_TYPE_FOR_EXTENSION`, `storage.ts`'s exported reverse of `EXTENSION_FOR_CONTENT_TYPE`; `1-year immutable` cache headers, safe since a given key's content never changes) — an app Route always wins routing priority over a stale `public/` entry for the same path, so this isn't a workaround for one Next.js quirk, it's the actually-correct fix regardless of host (an ephemeral/read-only production filesystem, which AWS Amplify's SSR compute plausibly is, would break the snapshot-serving approach the exact same way). Also fixed the CMS media library's own thumbnail/reuse flow, which shares this exact code path and had the identical latent bug — its own e2e test (`ops-cms-media.spec.ts`) never actually fetched the file it was asserting on, only DB rows and visible text, so it passed the whole time regardless. That test now does the same content-type fetch check `ops-cms-uploads.spec.ts` does.
- **The S3 bucket itself needs an externally-provisioned public-read policy** — same "external AWS review, not a code concern" class of gap as SES's sandbox approval. This app's code assumes it's already done; it can't provision that itself.
- **Two separate, easy-to-conflate Next.js body-size limits both had to be raised, not just one — found by reproducing directly against a `pnpm build && pnpm start` and reading the server's own console output, since the browser only ever shows an opaque digest-only "server error" page with zero detail.** `experimental.serverActions.bodySizeLimit` (default 1MB) governs the Server Action's own request body — raising only this let a >1MB file reach `uploadFileAction`, but an 11MB test file *still* crashed. The second limit, `experimental.proxyClientMaxBodySize` (default 10MB — this is Next 16's current name; `middlewareClientMaxBodySize` is the same setting's deprecated pre-v16 name, still functional but flagged `@deprecated` in the type definitions), governs how much of the body `src/proxy.ts` is allowed to see, and `/ops/cms/uploads` isn't under `/api/*` so Proxy runs on it same as everything else. Left at its default, the 11MB body got silently truncated to 10MB before ever reaching the Server Action's multipart parser, which then choked on the cut-off body ("Unexpected end of form") and crashed — a completely different failure mode than this action's own clean "too large" validation error, and one that only an 11MB (not e.g. a 2MB) test file exposed. Both are computed in `next.config.ts` from `MAX_UPLOAD_SIZE_BYTES` (`src/lib/uploads/constants.ts`) plus a 2MB overhead margin, matching the action's own cap rather than a second hardcoded `"12mb"` literal — a holistic code review flagged the original version's three independent numeric literals (the action's cap, and both Next.js config limits) as a real risk of this exact bug recurring the next time someone raises the upload cap without remembering both config settings exist. `next.config.ts` imports that constant via a **relative path, not the `@/` alias** — it's loaded directly by Next's CLI, outside the normal app module graph, and isn't guaranteed to resolve tsconfig path aliases the way route code does. **Watch for this exact two-limit trap on any future large-request feature** — raising only the more obviously-named one (`serverActions.bodySizeLimit`) looks like it fixed things (a smaller oversized file might even pass) right up until a large enough request hits the second, separately-defaulted limit.
- **Validation (content-type allowlist: JPEG/PNG/WebP/GIF/PDF; `MAX_UPLOAD_SIZE_BYTES`) lives in `uploadFileAction`, not `uploadFile()`** — the size cap is a named constant (`src/lib/uploads/constants.ts`, shared with `next.config.ts` — see above), not a `system_settings` row, since this is a technical/security limit rather than a business config value (matches how `rateLimit.ts`'s thresholds are hardcoded rather than admin-editable).
- **`writeAuditLog` (`CMS_FILE_UPLOADED`) was the only persisted upload record for a while — a real `uploaded_files` table now backs a full media library**, see the Media library implementation notes above.
- **Two entry points share one action**: the standalone `/ops/cms/uploads` page (linked from the CMS dashboard) is the one that matters for documents — upload a PDF, copy the resulting URL, paste it as a Markdown link into any page's content. `NewsPostForm.tsx`'s "Image URL" field also got an inline uploader next to it, calling `uploadFileAction` imperatively (Server Actions can be invoked directly from client code, not only via `<form action>`) rather than through a nested `<form>` (HTML doesn't allow nesting one inside `NewsPostForm`'s own form) — required promoting `imageUrl` from an uncontrolled `defaultValue` input to controlled state.

Seeded with placeholder copy; a `VOL_MKT`/`ADMIN` overwrites it via `/ops/cms/pages/[slug]` post-deploy. If the setting is unset, the action fails with a generic "try again later" message rather than leaking configuration state to a public visitor. - **A trap worth remembering for any future action that redirects a page back to the exact URL it was already on** (both `updateStaticPageAction` and `updateNewsPostAction` do this): in e2e tests, `page.waitForURL(sameUrlItStartedOn)` resolves immediately without waiting for the mutation to actually commit, since the URL already matched before the click. `e2e/cms.spec.ts` hit this for real (flaky on the static-page save, deterministically broken on the publish-toggle save) — fixed by polling the DB directly (`expect(async () => {...}).toPass(...)`) instead of trusting `waitForURL` whenever start-URL and redirect-target are the same.
- **A non-resource-scoped `/ops/*` RBAC denial (e.g. a non-`VOL_MKT` hitting `/ops/cms`) is caught by `src/proxy.ts` and redirects to `/dashboard` (200) — it never reaches the page's own `requireOpsRole`/`notFound()` check.** That's different from `/ops/check-in/*`'s pattern (a 404), because check-in's denial is *resource-scoped* (a specific session's assigned host) which Proxy's route-level `isAllowed()` can't express, so it falls through to the page level. Don't copy the check-in spec's "expect 404" pattern for a plain route-level role check — assert the `/dashboard` redirect instead.

## Admin-creatable static pages implementation notes

(see `src/app/pages/[slug]/page.tsx`, `src/app/ops/cms/pages/*`, `src/lib/cms/slugify.ts`):
- **No schema change — the gap was narrower than "extend `static_pages`."** The CMS *edit* flow (`/ops/cms/pages/[slug]`) was already fully generic, querying by whatever slug it's given; `home`/`about`/`contact` are just the three rows a migration happened to seed. The actual gaps were a missing *create* flow and a missing public route for anything beyond those three.
- **`RESERVED_STATIC_PAGE_SLUGS` (`src/lib/cms/slugify.ts`) is the one list gating all of this** — `home`/`about`/`contact` each have their own dedicated route doing more than a generic Markdown render (`home`: the upcoming-sessions list; `contact`: the contact form), so `createStaticPageAction` rejects them as a chosen slug, and the new generic public route 404s if asked for one of them — one canonical URL per page, no duplicate rendering. `publicPathForStaticPage()` (same file) is the single place that knows how a slug maps to its real URL (`home` → `/`, the other two reserved slugs → `/slug`, everything else → `/pages/slug`) — both the CMS dashboard's "View" links and `updateStaticPageAction`'s `revalidatePath` call use it.
- **`new` is in that same reserved list too, for a completely different reason than the other three — found by a holistic code review, not by a bug report.** It collides with the literal sibling route `/ops/cms/pages/new`: Next.js always prefers a literal route segment over a dynamic `[slug]` one for an exact match, so a page created with that slug would redirect straight back to the "create a new page" form instead of its own editor, on every subsequent Edit-link click — silently uneditable from the moment it's created. `e2e/cms.spec.ts` has a dedicated regression test for this exact slug, not just the other three.
- **Found and fixed a real, pre-existing bug in `updateStaticPageAction` while building this**: its `revalidatePath` call assumed every slug was a top-level route (`` `/${slug === "home" ? "" : slug}` ``) — true only for the 3 fixed pages, silently wrong (revalidating a URL that was never the actual page) for anything created via this new flow. Invisible until there was a second class of page to expose it.
- **Both `createStaticPageAction` and `updateStaticPageAction` also call `revalidatePath("/", "layout")`** (added by the same holistic review) — `SiteNav` lists every non-reserved page on nearly every route in the app, and revalidating just `/ops/cms` plus the one page's own path doesn't bust an already-visited page's cached RSC payload elsewhere. `"layout"` busts every route sharing the root layout, i.e. the whole app — cheap here since page create/edit is a rare admin action, not a hot path. Same Router Cache staleness class this codebase has hit and fixed several times before, just previously only ever needing a single specific path revalidated rather than "everywhere the data could be shown."
- **New pages are reachable from `SiteNav`, not just by typing the URL** — one more query per render (any `static_pages` row not in `RESERVED_STATIC_PAGE_SLUGS`, ordered by title, listed between Contact and Schedule). Unlike the existing auth-context query (which is gated behind a session check and skips guests entirely), this one is unconditional — it has to be, since these are public pages guests should see too — so it's a genuinely new per-request cost on every anonymous page view across the whole public site, not a reuse of existing work. Cheap in practice given the table's tiny size, but worth being accurate about.
- **`createStaticPageAction` mirrors `createNewsPostAction`'s exact shape** (title required, slug auto-derived via the existing `slugify()` unless overridden, catches Postgres `23505` on the slug's unique constraint rather than pre-checking it) — same reasoning, don't duplicate the pattern with different conventions.
- **`e2e/cms.spec.ts`'s new "create a page" test hit the same "does `waitForURL`'s regex actually mean what I think" trap this codebase has hit before, in a new shape**: `/\/ops\/cms\/pages\/[a-z0-9-]+$/` matches not only the real target URL but also the *starting* URL, `/ops/cms/pages/new` — "new" itself matches `[a-z0-9-]+`. The wait could resolve before any navigation happened at all, extracting `"new"` as the "slug" and then correctly 404ing at `/pages/new`. Fixed with a predicate function that explicitly excludes a path ending in `/new`, not a regex.

## Environment/build status banner implementation notes

(see `src/lib/envStatus.ts`, `src/components/EnvStatusBanner.tsx`):
- **Deployment-identity facts, not `system_settings`** — same reasoning as `src/lib/org.ts`: `APP_ENV`/`GIT_SHA` are plain env vars set once per instance, not runtime-editable business config.

- **`support_tickets.status` is a plain two-state enum (`Open`/`Resolved`), also confirmed with the user** — "needs staff reply" vs. "needs member reply" is derived by comparing `last_message_by_user_id` against `requester_user_id`, not a separate stored field. A member replying to a `Resolved` ticket auto-reopens it (inside `replyToTicketAction`'s transaction); a staff reply never changes status on its own — staff resolve explicitly via `resolveTicketAction`.
- **`last_message_at`/`last_message_by_user_id` are denormalized onto `support_tickets`** specifically so the "needs reply" check is a cheap single-row comparison everywhere it's used (the member's ticket list, the ops inbox sort, the member's notification banner, the staff nav badge count) rather than a join/subquery against `support_ticket_messages` in four different places.
- **`src/lib/support/actions.ts` is one shared module, not split ops/app-side** — `createTicketAction`/`replyToTicketAction`/`resolveTicketAction`/`reopenTicketAction` all touch the same two tables under the same transactional discipline (`BEGIN`/row-lock via `FOR UPDATE`/`COMMIT`, matching `bookSession`'s pattern). `replyToTicketAction` in particular is called from both `/app/support/[id]` and `/ops/support/[id]` via the same `ReplyForm` component (`src/components/support/ReplyForm.tsx`) — it re-derives whether the caller is the ticket's own requester or holds `VOL_SUPPORT`/`ADMIN` itself, never trusting which page the request came from.
- **Ordinary member ticket creation/replies are deliberately not audit-logged; a staff/admin reply is** (`SUPPORT_TICKET_REPLY`, plus `SUPPORT_TICKET_RESOLVED`/`SUPPORT_TICKET_REOPENED`) — matches the existing precedent that `system_audit_logs` records staff-observable/admin actions, not routine member self-service ones (booking/cancelling aren't audit-logged either).
- **Notifications reuse and extend the existing mechanism rather than adding a second banner component.** `PendingNotification` (`src/lib/notifications/getPendingNotifications.ts`) gained an optional `urgent?: boolean`; `NotificationBanner.tsx` applies a new `.notification-banner--urgent` red CSS modifier (new `--color-danger`/`--color-danger-hover` tokens in `globals.css`, both light/dark) when any pushed notification is urgent. The member's "a support ticket reply is waiting for you" entry is the first thing to ever set `urgent: true`.
- **The staff-side equivalent is a live count appended to the "Support" nav link label** (`"Support (3)"`), not a full-width banner on every ops page — computed in `SiteNav.tsx` via one extra query, gated behind `isAdmin || roles.includes("VOL_SUPPORT")` so ordinary members/guests never pay for it (unlike `extraPagesResult`'s unconditional query in the same component, which has to run for every visitor since those pages are public).
- **`/ops/support`'s status filter hits the exact `$1::text IS NULL OR enum_column = $1` trap CLAUDE.md already documents** (see the Admin passes implementation notes in `CLAUDE.md`) — fixed the same way, by casting the column (`t.status::text = $1`) rather than the parameter.
- **e2e's shared inbox is genuinely global, not scoped per test** — `e2e/support.spec.ts`'s badge-count assertion matches `/^Support \(\d+\)$/` rather than an exact count, and clicks into its own ticket by row (`getByRole("row", { name: subject })`) rather than a bare `getByRole("link", { name: "Needs reply" })`, since another parallel e2e worker's own open ticket can legitimately share the same inbox and the same "Needs reply" label at the same time.

## Check-in rebuild implementation notes

(see `src/lib/checkin/roster.ts`, `src/app/ops/check-in/page.tsx`, `SessionRosterCard.tsx`, `[sessionId]/page.tsx`):
- **`SessionRosterCard` is one component reused verbatim by both the new `/ops/check-in` overview (one collapsible card per upcoming session, today's session(s) defaulted open) and the pre-existing `/ops/check-in/[sessionId]` single-session route** — explicitly to avoid the "two entry points silently drift" pattern this codebase has hit before.
- **Polls `getCheckInRoster` every 10s while the tab is visible** (paused on `visibilitychange`) — this app has no WebSocket/SSE/pub-sub infrastructure anywhere, so polling a Server Function is the pragmatic "live" choice, not a fallback. Checkbox toggles apply optimistically via `setCheckedInAction` called directly from the client handler (not through a `<form>`), reverting on failure.
- **`getUpcomingCheckInSessions()` is host-scoped exactly like `requireCheckInAccess`** (CLAUDE.md's Ops workspaces notes): a `VOL_HOST` who isn't also `VOL_MBR`/`ADMIN` only sees sessions they're the assigned host of, `AND s.host_user_id = $1` appended when not privileged — the overview page can't accidentally leak a broader roster list than the resource-scoped per-session route already allowed.
- **"Member"/"first-timer" badges are both freshly derived per render, not stored flags.** Member reinlines the same `membership_expires_at > now()` check `roles.ts`'s `MBR` derivation uses (not imported directly — the row shape here differs from `UserRow`). First-timer is "no prior `checked_in = true` row anywhere for this user" — unioned across `passes`, `seat_reservations`, **and `legacy_attendance_history`** (a migrated member's real attendance history predates Phase 8's booking tables entirely; skipping that table would badge every migrated regular as a first-timer). Uses `session_id IS DISTINCT FROM $2`, not `!=`, since `legacy_attendance_history.session_id`'s FK is `onDelete: SET NULL` — a `!=` comparison would silently exclude a NULL-session legacy row instead of counting it as prior attendance.
